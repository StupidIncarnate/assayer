## Words used here

A **state leaf** is a condition leaf whose `operandFlow` holds a `repeat`. A **count** is how many passes of one loop
were completed when a leaf is read, or how many calls were made before the current call. A state leaf's meaning changes
with the count: `count < limit` is a different question on pass 0 and on pass 3.

## What to implement

1. **Steerable.** A state leaf is steerable when every parameter its flow names is an applied parameter (the existing
   flow rule, which already reads `valueExprParamsTransformer`) and every `repeat` in it has a literal or parameter start
   value and a literal, parameter or `element(parameter)` change. Anything else is unsteerable and its branch is admitted
   undriven as today.
2. **Which count a read means.** Read it from where the leaf's branch sits, using the branch lines, never source text:
   - a branch whose lines lie inside a loop's lines reads the pass being executed, so its count is that pass index;
   - a branch after the loop's end line reads the total passes the route made;
   - a branch before the loop's start line reads zero passes (the flow holds no `repeat`, so this does not arise);
   - a `per: 'call'` flow reads `calls - 1` calls before, where `calls` is the case's call count.
3. **Count bound.** Counts run from 0 (passes) or 1 (calls) up to
   `max(arrayCardinalityStatics.counts.many, <largest integer literal any state leaf compares with> + 1)`. Do not add a new
   statics file. A route no count within the bound makes feasible is KEPT and marked undriven. It is never dropped and it is
   never an `unreachable-exit` lint: "no tried count reached this arm" is not evidence (DESIGN.md "When is an arm
   unreachable?").
4. **Routes through repeated reads.** A route is the set of arms its passes (or calls) take, plus the values its run reads
   (README "The cause rule" step 4). For a state branch that can take both arms at different counts, add the combination in
   which it takes both, in count order, as one more route beside the one-arm routes. The case's `arms` list holds each
   (branch, arm) once, in the order first taken. For every candidate count, resolve each state leaf with `routeResolve` and
   its `repeats`, so the leaf becomes a leaf on a parameter (`limit gt 3`), and give the union of those requirements to
   `causeArrange`. Keep the first feasible count per distinct arm set, in ascending count order.
5. **Array changes.** A leaf still holding `repeat` over `element(param items)` after route resolve is settled here:
   candidate arrays come from the array sizes in `arrayCardinalityStatics` (empty, one, many). Item values come from the
   literal the leaf compares with, one above it and one below it, and the cause rule's edge values for the item type
   (`edgeValueStatics`, task 12.1.1). Evaluate the flow with `repeats.items` and decide the leaf with
   `evaluateConstPredicateTransformer`. Keep the first candidate per arm set. A one-item array carries the edge values. A
   many-item array is built so that one run takes as many arms as it can. Build each chosen array into the case's
   arrange value with `arrayArrangeTransformer` (task 14.2.3), which places an element per arm.
6. **Polarity.** `route-resolve` wants `armByBranch` in `then`/`else` terms (the `select` form). Build it from the route's
   arms as follows: for a branch with an `arms` list, the first listed arm is `then` and every other arm is `else`; for a
   branch with no `arms` list the label is already `then` or `else`. A `logical-assign` branch lists `kept` first, so the
   `select` that a `??=` leaves behind resolves correctly.
7. **`calls`.** Set `calls` (task 15.1.2) on every case of an entry that holds a `per: 'call'` state leaf, even when
   it is 1. Leave it unset on every other case. Include `calls` in the de-duplication signature, so two cases that differ
   only in `calls` are both kept.
8. **Nothing else changes.** Entries with no state leaf derive exactly the cases they derive today. Prove it with the
   existing tests, which must pass unchanged.

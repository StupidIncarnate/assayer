## Contract

Today the transformer answers `true` or `false`: every write is one the walk follows, or the variable is untracked.
It now answers with the class of the writes, so the statement reader (tasks 15.3.2, 15.4.1 and 15.5.1) knows which binding to build:

```ts
false | 'plain' | 'loop' | 'shared'
```

| Answer | Means |
|---|---|
| `false` | some write is one the walk cannot follow. The variable stays untracked and its branches stay undriven |
| `'plain'` | every write is a straight-line statement in the declaring function, inside blocks and `if`s only. A `const` (no writes) is `'plain'` |
| `'loop'` | exactly one write besides the initializer, and it is a direct statement of the body of one loop that sits in the declaring function |
| `'shared'` | the variable outlives one call of the function that writes it. Exactly one write, a direct statement of that function's body block |

Callers: `assign-binding-layer-transformer.ts` (line 34) and `read-value-expr-layer-transformer.ts` (line 119) test only
that the answer is truthy, so they compile and behave as before. The three non-false answers are strings, which are
truthy. This task edits neither caller.

## What to implement

1. **Writes that are followed.** The write target is an identifier, or `this.<field>` for a class field. The write sits in
   an `ExpressionStatement` whose expression is a `BinaryExpression` with the target on the left and one of these operator
   token kinds: `EqualsToken`, `PlusEqualsToken`, `MinusEqualsToken`, `AsteriskEqualsToken`,
   `QuestionQuestionEqualsToken`, `BarBarEqualsToken`, `AmpersandAmpersandEqualsToken`. An increment or decrement
   (`count++`, `--count`) is not followed: the answer is `false`.
2. **Declarations.** Accept a `let` (identifier name), a parameter, and a class `PropertyDeclaration` (not `static`, not
   `readonly`, identifier name). For a field, ask the checker for the field symbol's references and keep the write ones. A
   write reaches the field as `this.<name>`: the reference node is the name inside a `PropertyAccessExpression` whose
   expression is the `this` keyword.
3. **Class `'plain'`.** The write's statement reaches the declaring scope through `isWriteWithinScopeGuard`, as today.
4. **Class `'loop'`.** The write's statement is a direct child of a block that is the body of a loop statement (`for`,
   `for…of`, `for…in`, `while`, `do…while`), or is itself the unbraced body. The loop's parent then reaches the declaring
   scope through `isWriteWithinScopeGuard`. A write nested one container deeper than the loop body (inside an `if` in the
   body) is `false`: that write happens on some passes only, and the walk does not model it. A second write to the
   variable, anywhere, makes the answer `false`. A loop inside a loop makes it `false` (the guard does not cross a loop).
5. **Class `'shared'`, two shapes.**
   - The variable is declared outside the writer: a module-level `let`, or a class field. The one write is a direct
     statement of the body block of one function-like writer, and the writer is not the declaring scope. For a field the
     writer is a method of the same class.
   - The variable is declared in a function and the one write is a direct statement of the body block of a closure that
     the function returns (`return () => { calls += 1; … }`): the closure's parent is a `ReturnStatement`, or the closure is
     the concise body of the declaring arrow. The closure's own parameter list is empty.
   A shared write nested in an `if`, a loop or a `try` is `false`. Two writers are `false`.
6. Read the written statement's parent chain only through the existing guards and the one-step peels above. Use
   `readDeclaringScopeLayerTransformer` for the writer scope. Never call `getFirstAncestor` or scan descendants.
7. Update the header comment: the answer, the four classes, and the shapes of write that are not followed.

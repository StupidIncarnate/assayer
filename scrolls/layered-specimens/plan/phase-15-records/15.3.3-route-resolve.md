## Read first

`route-resolve-transformer.ts` and `value-expr-resolve-transformer.ts`. Route resolve settles what a leaf's local variable
holds on one route. Its only caller is `derive-cases-transformer.ts` (line 367). `value-expr-resolve` resolves a `select`
by the arm the route took and rebuilds every other form as `method`, so it throws on `apply`, `repeat` and `element`
(task 15.1.4). This task therefore settles the new forms before `value-expr-resolve` ever sees them, and `value-expr-resolve`
itself needs no edit.

## Contract

One new optional input, shaped as in task 15.2.2:

```ts
routeResolveTransformer({ requirements, armByBranch, params, repeats? })
// repeats?: { passes: ReadonlyMap<string, number>; calls: number; items: ReadonlyMap<string, readonly RepresentativeValue[]> }
```

`armByBranch` maps a branch id to `'then'` or `'else'`: the arm the route took, named by the polarity the `select` form
uses (`then` is the arm taken when the branch's condition holds). `derive-cases` does that translation for branches that
list other arm names, such as `logical-assign` (task 15.5.2).

**Settling.** Before a leaf's flow reaches `valueExprResolveTransformer`, walk it:

1. A flow with no new form goes to `valueExprResolveTransformer` unchanged, as today.
2. `apply`, `repeat` and `element` are settled child first. `repeat` and `element` become a `lit` through
   `valueExprEvaluateTransformer` with `repeats`, when their start value and change are literals. `apply` of two literals
   becomes a `lit`.
3. A `select` or a `method` that holds a new form below it makes the leaf undecided. The walk does not model it.
4. A `repeat` whose change is `element(param)` is left as it is, with `repeats` unused: the items are not known until the
   case builder picks them (task 15.5.2), so the leaf stays a derived requirement.

**Moving a comparison onto the parameter.** A state leaf compares a counter with a parameter (`count < limit`), so its
flow is `apply(subtract, left, right)` and its predicate compares with `0` (tasks 15.3.5 and 15.7.3). After settling, when one side is
a number `lit` and the other side is a `param`, rewrite the leaf to read the parameter and compare it with the literal:

| Leaf predicate on `left - right` | Left side is the literal `c` | Right side is the literal `c` |
|---|---|---|
| `gt 0` | param `lt c` | param `gt c` |
| `gte 0` | param `lte c` | param `gte c` |
| `lt 0` | param `gt c` | param `lt c` |
| `lte 0` | param `gte c` | param `lte c` |
| `eq 0` | param `eq c` | param `eq c` |
| `neq 0` | param `neq c` | param `neq c` |

The rewritten leaf has `operandParamName` set to the parameter, `operandType` set to the parameter's type from `params`,
the new predicate, and no `operandFlow`, exactly as the existing code rewrites a leaf whose flow is a bare `param`. A
parameter missing from `params` is undecided. Two literals fold to one constant and take the existing welded-constant
path. Two parameters stay a derived requirement, which task 15.6.1 arranges.

Everything else keeps its current behaviour: `undecidable` is true when any leaf is undecided, `derived` lists the
leaves that are functions of parameters.

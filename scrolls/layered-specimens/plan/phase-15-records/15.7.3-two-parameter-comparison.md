## What to implement

Task 15.3.5 reads a comparison of two operands when at least one holds a `repeat`. Extend the same rule: a comparison whose
two sides are both **plain parameters of a number type** (`count > limit`) is read the same way, with no `repeat` needed.

- Both sides are identifiers that read as `{ kind: 'param', name }` (the context's `params` name them and every write to them
  is followed), and both parameters have the descriptor `{ kind: 'number' }`.
- The leaf carries `operandFlow = apply(subtract, param left, param right)`, `operandType: { kind: 'number' }`, no
  `operandParamName`, `operandPropertyPath` or `operandTypeRef`, and the predicate `{ kind, literal: 0 }` with the kind that
  follows the operator (`gt`, `gte`, `lt`, `lte`, `eq`, `neq`).
- A parameter of a string type, a literal union, a union or an optional type keeps the comparison `unrecognized`, as today.

Remove the sentence "A comparison of two plain parameters is left as it is" from the header comment and describe the rule.

## Tests

- `VALID: count > limit with number parameters => apply(subtract, param count, param limit), predicate gt 0, no param name`
- `VALID: count < limit, count >= limit, count <= limit, count === limit, count !== limit => lt, gte, lte, eq, neq`
- `VALID: the task 15.3.5 cases with a counted side still give the same leaves`
- `INVALID: count > limit with string parameters => unchanged (unrecognized)`
- `INVALID: count > limit where limit is number | undefined => unchanged`
- `INVALID: count > other where other is a local not tracked => unchanged`
- `EDGE: the existing test that expects count > limit with two plain parameters to be unrecognized => rewritten to expect the new leaf`
- `EDGE: every other existing test passes unchanged`

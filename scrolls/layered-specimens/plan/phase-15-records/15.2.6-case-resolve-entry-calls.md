## Contract

`caseResolveEntryBroker` gains one optional input, `calls?: number`, the case's call count (task 15.1.2). It is the
same value the shim passes (`calls: testCase.calls`, task 15.3.4).

- `calls` undefined: the broker behaves exactly as today.
- `calls` defined: the case is a call sequence on a freshly loaded module. The broker still decides from `subject` whether
  the entry exists, and returns `undefined` when it does not, as today. When it exists, the broker returns a drivable
  entry that behaves as follows.
  1. On its first application it loads the module through `requireFresh()` (awaiting the result, so both module formats
     work), resolves the real entry from that fresh module with the same access rules and the same `construct` input, and
     keeps it. A method's instance is therefore built once per case, and every later application reaches the same instance.
     Every later application reuses the kept entry and does not call `requireFresh` again.
  2. On the first application it applies the real entry to the arguments. If the result is a function that declares no
     parameters (`length` is 0), it is a returned closure. The wrapper keeps it and returns the closure's own result, and
     every later application calls the closure with no arguments. If the result is anything else, every later application
     applies the real entry to the arguments again.
  3. A returned function that declares parameters is not a closure this broker drives. Its result is returned as it is.
- Access kind `module`: `requireFresh` is already the entry. Return it as today, whatever `calls` says.

The wrapper is asynchronous. The interpreter finishes every application through `caseSettleBroker`, which awaits a
promise.

## What to implement

1. Add the input and the wrapper. Hold the kept entry and the kept closure without mutating a shared variable the lint
   rules forbid: a single object created per resolve call, or a lazily created promise, are both fine.
2. Reuse the existing access-kind code by calling the same resolution on the fresh module. Do not copy it.
3. Update the header comment: the call-sequence behaviour, the closure rule, and why freshness is tied to `calls`.

## Tests

- `VALID: calls 2, named access => requireFresh is called once and the fresh module's function is applied on both applications`
- `VALID: calls 2, method access => both applications reach one instance (a counter field reads 1 then 2)`
- `VALID: calls 2, entry returns a no-parameter closure => the first application returns the closure's result, the second calls the closure again (its captured counter reads 1 then 2)`
- `VALID: calls 2, entry returns a closure that takes a parameter => the closure itself is returned both times`
- `VALID: calls 2, entry returns a plain value => the entry is applied twice`
- `VALID: calls 2, ESM requireFresh returning a promise => resolves the fresh module and applies it`
- `VALID: calls undefined => every existing expectation is unchanged`
- `VALID: calls 1 => the module is still loaded fresh`
- `INVALID: calls 2 and the subject lacks the entry => undefined`
- `EDGE: access module with calls => requireFresh is returned, as today`
- `EDGE: access through-caller with calls => resolves the caller on the fresh module`

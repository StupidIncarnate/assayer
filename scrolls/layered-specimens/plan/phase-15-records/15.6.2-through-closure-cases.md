# 15.6.2 Cases for a returned closure, driven through its host

- **Phase:** 15, Core: compound assignment, loop-written variables, call sequences. **Row:** #6, in parallel with 15.6.1 and 15.6.3. No task of the row depends on another task of the row.
- **Depends on:** row #5 (task 15.5.2 counts calls in `derive-cases`).
- **Model:** default (the worker's default model; this task is fully specified).
- **Covers:** DESIGN.md section "Shared mutable state" ("a variable a closure captures and changes"); the `closure-capture` value of the shared-state axis; `packages/core/CLAUDE.md` section 4 "Drive an inline function that nothing calls by name".

`follow-calls-transformer.ts` treats a returned inline function as undriven (`REACHED_FN_REASON`) because its parameter is set
by whoever applies it. A returned closure with **no parameters** has no such parameter: its branches read the host's
parameters and the variables it captures, so a case can decide them. This task derives its cases. Task 15.7.1 routes to it.

## Contract

```ts
throughClosureCasesTransformer({ closure, host, label? }): ThroughCallbackCases
// closure: ScopeRecord   the returned function with no parameters
// host:    ScopeRecord   the reachable scope that returns it
```

## What to implement

1. Derive the closure's cases with `deriveCasesTransformer` over the **host's** parameters (`appliedParamsTransformer`), the
   closure's branches and exits, `envDrivable: false`, no harness. Build the request with `deriveCasesRequestTransformer`, as
   `throughCallbackCasesTransformer` does. The leaves of the closure name the host's parameters (task 15.4.3), and its shared
   variable carries a per-call `repeat` (task 15.5.1), so `derive-cases` sets `calls` on each case (task 15.5.2).
2. A case's `reachesPath` is the closure's own exit. The interpreter judges the last application, and the host's own exit
   fires only in the first one (task 15.2.6), so the closure's exit is the tail of the observed path in every case.
3. The entry keeps the closure's identity (name, scope path, exits) with access `through-caller`, `callerName` the host's
   name and params the host's. The harness resolves the entry by calling the host once and then the closure (task 15.2.6).
4. A host parameter the fill seam refuses is returned on `unfillable`, with the host as owner, as the callback twin does.
5. Header comment in plain words: what a returned closure is, why only a no-parameter one is driven, what `calls` means.

## Tests

Build scope records by hand with the stubs the other `through-*` tests use. Assert the arm lists, the counts and `calls`.

- `VALID: card state/module-let's closure twin (host makeCounter(limit), closure leaf apply(subtract, apply(add, repeat call(0, add 1), 1), param limit) gt 0) => five cases, each with calls, arms then or else, the fewest-runs set holds one case`
- `VALID: the entry is a through-caller entry named for the closure with the host's params`
- `VALID: every case's reachesPath is the closure's exit alone`
- `ERROR: a host parameter the fill seam refuses => returned on unfillable with the host as owner`
- `EDGE: a closure with no branch => no cases and nothing reported`
- `EDGE: a closure that takes a parameter => returns no cases (the caller does not route it here)`

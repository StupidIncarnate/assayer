# 27.2 Fan-out: the fixes the user's answers ask for

- **Phase:** 27, settle the disputed cards. **Row:** #2, a fan-out row.
- **Depends on:** row #1 (27.1.1 lists each answered question and what it changes).
- **Model:** opus for each `27.2.<n>` task (a fix whose cause is a design answer is debugging work).
- **Covers:** README "Open questions for the user"; task 7.4 (how a card fix is made).

## How the fan-out works

This file is the one definition of row 27.2. There is no task `27.2` itself. Task 27.1.1 records, for each answered
question, the one group harness or the one generator file the answer changes.

1. For each, the operator writes a real task file, `phase-27-disputed/27.2.<n>-<slug>.md`, in the format of every other
   task file: the id, the phase, the row, `Depends on: 27.1.1`, a Files table of 1 to 3 files (a generator file with
   its test, or one group harness), the answer it applies, the commands below, and "Done when". It adds the ids to the
   README tracker row before it dispatches them.
2. No two tasks of the row edit one file. Two answers that change one file are one task.
3. Task 27.3.1, in the row after, removes the cards' exclusion entries.

## What each worker does

Task 7.4's "What each worker does", with the user's answer in place of the card text it would otherwise follow. Never
edit DESIGN.md: the user does that.

## Verify

```
npm run ward -- -- <every file the task changed>
npm run ward -- --only integration -- packages/specimen-generator/src/startup/start-specimen-generator.integration.test.ts
npm run generate:specimens -- --check
```

## Done when

Every command exits 0. The card the task fixes passes the card check once task 27.3.1 removes its exclusion entry.

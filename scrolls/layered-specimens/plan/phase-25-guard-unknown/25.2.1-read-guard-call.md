## What to implement

A condition that is a call `guard(arg)` reads as a `narrows-to` leaf when all of these hold, decided from the type graph and never from names or text:

1. The callee resolves, by symbol, to a function declared in the same file: a `function` declaration, or a `const` bound to an arrow or function expression.
2. That function's declared return type node is a type predicate (`value is number`, a `TypePredicate` node), and the predicate's parameter name is the callee's parameter at the argument's position.
3. The argument is an identifier that names a parameter of the entry (`operandParamName`), or a property chain rooted at one.

The leaf has:

- `operandParamName` the argument's parameter (and `operandPropertyPath` for a chain);
- `operandType` the argument's declared type (for card `retype/guard`: `unknown`);
- `predicate: { kind: 'narrows-to', narrowsTo: <the descriptor of the predicate's type node> }`, read through `read-type-fact` and `type-descriptor`.

The declared predicate is the author's statement. This reading takes precedence over any reading of the callee's body: a guard whose body is a single comparison (`typeof value === 'number'`) is still read as `narrows-to`, so the body cannot give a different answer. A call with no type predicate keeps its present reading. An imported guard keeps its present reading too (cross-file composition is not part of this phase).

`!guard(value)` and `guard(a) && other` need no change: the condition tree already wraps the leaf in `not` and `and`.

Formatting must not move the leaf: the readout and the coverage ID key on the call's structural projection (`project-node`), never on text.

## Contract

`walkContextContract` gains one optional field, `inCondition: z.boolean().optional()`. Absent means `false`. It is
omitted rather than stored as `false`, the same way `enclosingClass` and `bindings` are omitted when empty, so a
context built without it stays strictly equal to a context that never had the key. That keeps the stub, the contract
test and every existing golden assertion unchanged.

## What to implement

1. `walkContextTransformer` takes a new optional input `condition?: boolean`. When it is `true`, the returned context
   carries `inCondition: true`. When it is absent, the returned context inherits the field from `context`. When
   `scopeSegment` is set (the walk enters a function or class), the field resets to absent. A function defined inside a
   condition does not run as part of it, which is the same reason `guardPath` resets.
2. Add one sentence to the file's PURPOSE block: a node is in a condition when the nearest enclosing `if` test,
   ternary condition or `switch` subject contains it, and a nested scope ends that.
3. No handler sets `condition` in this task. Task 11.2.x does. Nothing reads the field yet, so no analysis changes.

## Tests

In `walk-context-transformer.test.ts`:

- `VALID: {root context} => inCondition is absent`
- `VALID: {condition: true} => inCondition is true and every other field is unchanged`
- `VALID: {context already in a condition, no condition input} => inCondition stays true`
- `VALID: {context in a condition, scopeSegment: 'inner'} => inCondition is absent`
- `EDGE: {condition: false after condition: true} => inCondition is absent`, so a caller can clear the field. This
  is the only way a later task opts a descent back out, so say it in the transformer's JSDoc.

## What to implement

1. The handler emits one branch of kind `ternary` per decision. For `a op b`:
   - the branch condition is read through the condition lens exactly as `read-conditional-exit` reads the same
     operator: for `&&` and `||` the left operand's truthiness, for `??` the left operand's non-nullish leaf
     (`read-nullish-leaf`). Use `readConditionTreeLayerTransformer`, as `handle-ternary` does.
   - the coverage ID is `coverageIdTransformer({ scopePath: context.scopePath, segment: `ternary:${projectNodeLayerTransformer({ node: <the left operand> })}` })`,
     the exact call `read-conditional-exit-layer-transformer.ts` makes for the same operand (lines 114 to 116), so one
     operator keeps one ID whichever lens reads it (section 5.12). Both files call the same two transformers with the
     same arguments; neither copies the other's string building.
2. Arm meaning, from README "The report vocabulary": `&&` takes `then` when the left is truthy (the right operand is
   evaluated), `else` when it stops at the left. `||` takes `then` when the left is truthy (it stops), `else` when the
   right is evaluated. `??` takes `then` when the left is non-nullish (it stops), `else` when the right is evaluated.
3. Descents, by the pieces table's slots. For `&&` and `||` the left slot is a condition, so the left operand descends
   under the enclosing guards with `tail: false` and `condition: true` (task 11.1.1): a logical operator inside it is a
   leaf of this decision, never a branch of its own. For `??` the left slot takes the operator's own position, so the
   left operand descends with `tail: false` and no `condition` marker. The right operand descends under the guard step
   of the arm that evaluates it (`&&`: `then`; `||` and `??`: `else`), with `tail: false`. Build every
   context with `walkContextTransformer` (section 5.5). The right operand's context carries no `condition` marker, so a
   `??` nested in a right operand is a value-position branch of its own.
4. Fall-through: both arms meet again at the enclosing statement, so the handler emits no exit. Record each arm as a
   fall-through arm the way `handle-ternary` does (`fallthroughArmContract`, the span of the operand that arm runs; the
   stop-at-left arm has no operand of its own, so record the right operand's span only for the evaluating arm and the
   left operand's span for the stopping arm).
5. A chain of one operator, `a && b && c`, is flattened with `flattenShortCircuitLayerTransformer({ expression, operator })`
   into one branch per decision, each nested in the arm that evaluates the next operand, the same shape the exit lens
   builds at `read-conditional-exit-layer-transformer.ts:88`. A mixed chain, `a && b || c`, is read at its root operator
   only: the root `||` is one decision, and its left operand `a && b` descends with `condition: true` (step 3), so it is
   two leaves of that decision and adds no branch.
6. Probe sites: take them from the condition readout, as `handle-ternary` does.
7. The steerability gate stays in `derive-cases` (section 5.12). This handler decides nothing about drivability.
8. The handler is not reached for an operator inside a condition. That is the dispatch route's job (task 11.4.1, which
   reads `context.inCondition`). Do not test `inCondition` here.

Write the PURPOSE block in plain words: what a value-position logical operator is, what the two arms mean, and why the
handler emits no exit.

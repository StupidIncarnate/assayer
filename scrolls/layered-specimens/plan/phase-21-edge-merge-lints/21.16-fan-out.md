# 21.16 Fan-out: the specimen tests that gain an edge-value merge lint

- **Phase:** 21, core: the edge-value merge lint family. **Row:** #16, a fan-out row.
- **Depends on:** row #15 (21.15.1), and rows #1 to #14.
- **Model:** opus for each `21.16.<n>` task (the cause of each failure is found by reading it, so it is debugging work).
- **Covers:** README "The core phase template" step 4; `packages/core/CLAUDE.md` section 6.

## How the fan-out works

This file is the one definition of row 21.16. There is no task `21.16` itself. Rows #2 to #5 and #12 to #14 report the six edge-value merge lints and give a mixed-plus operand its rule-named value. A specimen with an `if` on a `number | undefined`, a `||` on a string, a loose `==`, a `typeof` check on a nullable, a mixed `+` or a global `isNaN` gains a lint.

1. The operator runs `npm run test:syntax` once and lists every failing specimen test.
2. The operator groups the failures, at most 3 files a group: a specimen's `*.test.ts` counts as one file, and a
   registry line counts as `packages/core/test/harnesses/specimen-registry.ts`. Only one group of the row may hold the
   registry. A specimen whose verdict changes (it moves between `happy-path/` and `sad-path/`) takes its `.ts`, its
   `.test.ts` and the registry: three files, a group of its own.
3. For each group the operator writes a real task file, `phase-21-edge-merge-lints/21.16.<n>-<slug>.md`, in the format of every
   other task file: the id, the phase, the row, `Depends on: <the tasks above>`, the Files table naming each file,
   the specimen code each test reads, the commands below, and "Done when". It adds the ids to the README tracker row
   before it dispatches them.
4. The `21.16.<n>` tasks run like any other row: up to 3 workers at a time, and the row is committed once every
   task is done and `npm run ward -- --changed` exits 0.

## What each worker does

1. Read the specimen file first, then its test.
2. Rewrite each expected value from the DESIGN.md card the specimen matches and from the specimen's own code, never
   from the run's output (brief rule 19; `packages/core/CLAUDE.md` section 6, "Author that declaration by reading the
   specimen file yourself").
3. A failure that the core change of this phase does not explain is a bug in that change. Stop and report it in
   `OPEN`, with the specimen and the assertion. Never edit a source file under `packages/` here.

## Verify

```
npm run test:syntax
npm run ward -- -- <every file the task touched>
npm run ward -- --only integration -- packages/core/src/brokers/analyze/file/analyze-file-broker.integration.test.ts
```

## Done when

`npm run test:syntax` passes for every specimen of the group, and the two ward commands exit 0. When the last group of
the row lands, `npm run test:syntax` is green.

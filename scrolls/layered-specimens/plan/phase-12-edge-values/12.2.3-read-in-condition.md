## What to implement

1. A binary expression whose operator token kind is `InKeyword` reads as a leaf with predicate
   `{ kind: 'has-property', literal: <name> }`. The left operand must be a string literal; read the name through
   `getLiteralValue()`, never from the quoted spelling. The leaf reads the property the `in` names as an object-member
   operand of the RIGHT operand: `operandParamName` is the right operand's root parameter, `operandPropertyPath` is the
   right operand's own property path (empty for a bare parameter) followed by `<name>`, and `operandTypeRef` is set the
   way an object-member read sets it today (`readPropertyPath`). So `'label' in options` is the object-member read
   `options.label` with predicate `has-property`, and `'label' in config.display` is `config.display.label`. This is what
   lets the stub overlay arrange the object parameter (`packages/core/CLAUDE.md` section 9, `stub-realize`) exactly as it
   does for `config.mode === 'a'`. `operandType` is the declared type of that property when the receiver's type declares
   it (read it through `read-operand-type`), so edge values of the property's type are known; otherwise `unknown`. A left
   operand that is not a string literal reads as `unrecognized`, as before.
2. A comparison whose operator token kind is `EqualsEqualsToken` or `ExclamationEqualsToken` against a literal sets
   `loose: true` on the leaf's predicate (`eq` or `neq`). The comparison `x == null` and `x != null` keep the reading
   they have today: they are the nullish check, and carry no `loose` flag. If the reader does not classify `==` as `eq`
   today, classify it exactly as `===` and add the flag, and say so in your reply.
3. A comparison with `===` or `!==` carries no `loose` key.
4. Update the PURPOSE block and the USAGE lines.

## Tests

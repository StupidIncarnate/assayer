## What to implement

`readPropertyPathLayerTransformer` walks a `.member` chain down to its root (`config.mode` gives root `config`, path
`['mode']`). An element access is not walked: `counts[0]` is its own root with an empty path, so `read-condition`
records no parameter for `counts[0] > 2`, and the branch can never be driven.

Add one case before the final `return`: an `ElementAccessExpression` whose argument is a numeric literal walks into its
expression like a property access, and appends the segment `'[<n>]'`, where `<n>` is the argument's value read through
`getLiteralValue()` (never its text). So `counts[0]` gives root `counts`, path `['[0]']`, and `orders[0].prices[1]` gives
root `orders`, path `['[0]', 'prices', '[1]']`. An element access with any other argument (`counts[i]`, `counts['a']`)
stays its own root, as today.

The segment form `'[<n>]'` is the one every later task reads: task 12.6.2 pins an array for it, task 12.7.1 lets the
steerability gate drive it, and tasks 14.2.1 and 14.2.4 write the loop item the same way (`'[0]'`). A member name can
never start with `[`, so the two kinds of segment never collide. Write that in the PURPOSE block.

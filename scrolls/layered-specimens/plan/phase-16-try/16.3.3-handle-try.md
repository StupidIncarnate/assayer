## Words used here

A **throw point** is a place in the try block where execution can leave the block by throwing. The handler recognises
three:

1. a call to a same-file function whose body starts with guard clauses, `if (<cond>) { throw … }` or `if (<cond>) throw …;`
   (the then-arm is a `throw` and there is no else). The call throws when the OR of its guard conditions holds. Every leaf of
   those conditions must read a parameter of that function, and the call must pass an entry parameter straight into it, so
   that `rebasePredicateConditionTransformer` can move the condition onto the entry's parameters. A call that fails any of
   this is an opaque point;
2. an `await` of a call as in 1, when the callee is `async` (its throw is a rejection the `await` rethrows). An `await` of
   anything else is an opaque point;
3. a `throw` statement that sits in the try block directly or under `if`s inside it. It throws when the conjunction of the
   enclosing `if` arms holds. A `throw` with no enclosing `if` is an opaque point.

An **opaque point** is a leaf with predicate `unrecognized` and `operandCallPosition` set to the call or `await`'s position,
so `derive-cases` admits the branch undriven. Other calls (`console.log(x)`) are not throw points: nothing in the file says
they throw.

## Contract

Input: a `TryStatement` and the walk context. Output: a `HandlerResult` with `branches`, `nodes` and `descents`.

When the statement has **no catch clause**, or when the try block holds **no throw point**, the handler emits no branch.
It descends the blocks under the enclosing guards, because no arm of anything decides which block runs. Otherwise it emits
one branch:

| Field | Value |
|---|---|
| `coverageId` | `coverageIdTransformer({ scopePath, segment: 'try:' + <structural projection of the try block> })`, using `projectNodeLayerTransformer`. Never source text |
| `kind` | `'try'` |
| `arms` | `['finishes', 'catches']` |
| `condition` | holds when the block **finishes**: `and(not(p1), not(p2), …)` over the throw points in the order execution meets them (source order, depth first). One point gives `not(p1)` |
| `guardPath` | `context.guardPath` |
| `startLine`, `endLine` | the statement's lines |

The first arm is the one taken when the condition holds. Confirm that against `branch-arm-options-transformer.ts` as phases 13
to 15 left it. If it reads `arms` another way, follow it and report.

`conditionCauses` of `and(not(p1), not(p2))` wanted false gives one cause per point: `p1` true, and `p1` false with `p2` true.
That is how "point k throws and none before it does" becomes one route per point, with no special case in `derive-cases`.
Leaf ids follow `read-condition-tree`: the branch id plus a positional path, `#leaf.<point>.<n>…`.

Descents:

- the **try block under the enclosing guards**, with no `finishes` step. The block runs whichever arm is taken, up to its
  throw point. This also keeps a call inside it unconditional (`guardPath` empty), so `follow-calls` still drives a private
  callee such as `checkLow(count)` through the entry. An exit inside the block therefore carries no `try` step, and the exit
  a route reaches is chosen by the longest guard path the route satisfies: on a `catches` route the catch block's exit
  (one step) is longer than a `return` at the end of the try block (none);
- the catch clause's block, under `{ branchCoverageId, arm: 'catches' }`;
- the finally block, under the enclosing guards only: it runs on both arms.

All three blocks descend with `tail: false`. A try statement is accounted for only when every path through it returns or
throws (`read-accounted`, task 16.2.2), so the enclosing scope mints the one end-of-scope exit itself. A nested `if` that
saw `tail: true` would mint completion exits of its own, and the probe of a second exit would fire on the same run.

**Absorbed exits.** A `throw` in a `try` block with a `catch` clause never leaves the scope, and a `return` or `throw` in a `try`
or `catch` block never leaves it when the `finally` block always exits. The handler tells the walk through `absorbs`
(`walkContextTransformer`, task 16.2.1):

| Block | `absorbs` on its descent |
|---|---|
| try block | `'exit'` when the finally block is terminal (`readTerminalLayerTransformer`, task 16.2.2). Otherwise `'throw'` when the statement has a catch clause. Otherwise none |
| catch block | `'exit'` when the finally block is terminal. Otherwise none, because a `throw` in a catch block leaves the scope |
| finally block | none |

Handlers that emit exits (`handle-exit`, task 16.3.1, and `handle-block`, task 16.3.2) mint none for an absorbed statement.
That is what lets a `throw` under an `if` inside the try block coexist with the catch block's exit: the `throw` owns no exit,
so a `catches` route reaches the catch block's exit alone.

The handler emits one walk node of the statement's kind with `handled: true`, which removes the dark spot.

## What to implement

1. The handler, with the point reader as private recursive constants inside the file. The reader recurses over `Block`,
   `IfStatement`, `ExpressionStatement`, `VariableStatement` initializers, `ReturnStatement` and `ThrowStatement`
   expressions, `AwaitExpression`, `CallExpression` (callee and arguments), and parentheses, `as` and `!` wrappers. It uses no
   descendant scan and no ancestor climb. A call nested in any other expression kind is not found. Say so in the header.
2. To read a callee's guard clauses, build the callee's parameter descriptors from the entry parameters its call passes
   straight through (a copy of the entry's descriptor under the callee's parameter name), and read the guard's condition with
   `readConditionTreeLayerTransformer` in a context that carries them. Then rebase it with
   `rebasePredicateConditionTransformer` (`toCallerParam` maps the callee name to the entry's name).
3. The empty proxy, in the same shape as the other handlers' proxies.
4. Header comment: the throw points, the arms, why `finishes` is the true side, why the try block carries no step, and the
   absorbed-exit rule and the known limit below.

## Known limit (state it in the header and in your reply)

- A call nested in an expression kind the reader does not recurse into is not a throw point.

- `VALID: a finally block descends under the enclosing guards only`

- `VALID: a try with a catch clause and a finally block that always returns => the try and catch descents carry absorbs 'exit', the finally descent none`
- `VALID: a try with a terminal finally and no catch clause => the try descent carries absorbs 'exit'`
- `VALID: a try with a finally that can finish and no catch clause => no absorbs on any descent`
- `VALID: a throw inside an if inside the try block => a point whose condition is the if's condition`
- `VALID: await load(count) where load is an async guard-clause function => a point as for a call`
- `VALID: await somethingElse() => an opaque point (unrecognized leaf with operandCallPosition)`
- `VALID: a callee that takes a literal argument => an opaque point`
- `VALID: a try with a catch and no throw point => no branch; both blocks descend under the enclosing guards`
- `VALID: a try/finally with no catch => no branch`
- `VALID: a try statement that is the last statement => every block still descends with tail false`
- `EDGE: formatting immunity => the same try written with different whitespace and parentheses gives the same coverage id and condition`
- `EDGE: a guard clause whose condition reads a local, not a parameter => an opaque point`
- `EDGE: two calls in one expression statement => two points in left-to-right order`
- `EDGE: a call inside a template literal => not found, no point (the documented limit)`

The handler already puts every throw point into the branch's condition, so the engine's existing machinery gives one `catches`
route per point: `conditionCauses` of that `and` wanted false yields "point 1 throws" and "point 1 does not, point 2 does",
and wanted true yields "no point throws". This task proves that end to end and closes the places in `derive-cases` that
still assume a branch has the arms `then` and `else`.

## What to implement

1. The list of undriven arms (`undrivenArms`, built from `["then", "else"]` near line 293) and the known-arm choice beside it
   read the arms of each branch from `branch.arms` when it has them, and `then`/`else` otherwise. If tasks 13.x to 15.x already
   did this, change nothing and say so. Never invent a fallback arm: a case's arm labels are the arms its arranged input takes.
2. A `try` branch with one opaque point is unsteerable as a whole (the steerability gate already requires every leaf to be
   arrangeable). Both of its arms are declared routes and are undriven. The admission keeps the generic cause
   `unarrangeable-operand`, which is accurate: the deciding value is a call or `await` result that no case can set. Do not
   add a new cause.
3. An `await` throw point is exactly such an opaque point unless its callee is an `async` same-file guard-clause function
   (the handler rebases that one). A case cannot arrange a rejected promise, so an `await` of a parameter promise stays an
   opaque point. Say that in the header comment.
4. Check the exit a route reaches. A `return` in the try block carries no `try` step (the handler descends the block under
   the enclosing guards), and the catch block's exit carries `catches`. A `finishes` route satisfies only the unguarded
   exit. A `catches` route satisfies both, and the "maximal guard path" rule picks the catch block's exit because its
   guard is longer. Add no code unless a test shows it picks wrongly.
5. A `catches` route that no value can reach (the point's condition contradicts an earlier point's) is dropped by the
   existing emptiness check, never reported as a lint: an unreachable catch route is not evidence that the catch block is
   dead (DESIGN.md "When is an arm unreachable?").

- `VALID: card try/alone (try condition and(not(count lt 0), not(count gt 100)), exits ok [no try step] and failed [catches]) => five cases: finishes for count 50, 0 and NaN; catches for count -1; catches for count 101`
- `VALID: the catches case for count 101 requires count not below 0 (it is the second point, reached only when the first did not throw)`
- `VALID: every case is driven; the finishes cases reach the ok exit and the catches cases the failed exit`
- `VALID: a try block with two returns and a throw point between them => each route reaches the one exit its arms satisfy, and a route that satisfies two exits of equal guard length is dropped, never guessed`
- `VALID: card try/alone with the folded callee branches => fewest runs holds 3 cases: one finishes case, count -1 (checkLow then, catches) and count 101 (checkLow else, checkHigh then, catches)`. Core follows the same-file callees `checkLow` and `checkHigh` and folds their `if` branches into the entry, the way `funnel-named-cases` folds a same-file private into its caller (`packages/core/CLAUDE.md` section 4, "Drive an inline function that nothing calls by name"). So the entry's cases carry the callee arms beside `finishes` and `catches`, and the fewest-runs cover must take every one of the six arms: `checkLow` then and else, `checkHigh` then and else, `finishes`, `catches`. Build the test's branch list with the two callee branches in it, as the fold gives them. The card says 3, and this test holds core to 3.
- `VALID: a try with one opaque point => both arms are routes, both undriven, and undrivenBranches holds one entry with cause unarrangeable-operand`
- `VALID: a try with one steerable and one opaque point => the whole branch is undriven`
- `VALID: a catches route whose point contradicts an earlier point => dropped, and no unreachableExits entry`
- `EDGE: a try branch with arms and an if branch with none in one entry => each branch's undriven arms use its own labels`

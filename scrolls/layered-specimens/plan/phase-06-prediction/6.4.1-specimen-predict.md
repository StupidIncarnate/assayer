## Contract

```ts
specimenPredictBroker({ plan, files }): { report: SpecimenReport; today: string[] } | { refused: string }
```

- `files`: `{ relPath, content }[]`, every file the plan renders (`specimenFilesTransformer`, task 5.4.1), including the
  stub JSON and the harness file.
- `refused`: the engine refuses the specimen by name, the way TypeScript refuses a file. The caller writes it to
  `REFUSED.md` with this sentence (task 9.2.1) and writes no folder for it.

## What to implement

1. **Probe.** Select the analysed files (`entry.ts` and its siblings, never the harness, the test or JSON).
   `probeSourceTransformer` (task 6.2.2) gives the table.
2. **An import that cannot resolve.** When the plan's `file-boundary` value is `unresolvable-specifier`,
   `unresolvable-dynamic` or `unresolvable-no-types`, nothing runs: routes are empty, `fewestRuns` is 0, and the
   admissions come from task 6.2.4 alone (a build error, no undriven). Skip steps 3 to 6.
3. **Inputs.** `candidateInputsTransformer` (task 6.2.1). When it returns `refused`, nothing runs. Routes are empty,
   `fewestRuns` is 0, and task 6.2.4 names the gap. There is no cap on the number of inputs.
4. **Execute.** Build `entry` and `standIns` from the plan and the generator's parse of `entry.ts`: the root piece's
   `reach`, the constructor arity, the returned closure's parameter types, and for each package or built-in callee
   the ordinary and edge values of its declared return type. Run `specimenExecuteBroker` (task 6.3.1).
5. **Capped.** When any trace has outcome `capped`, return `{ refused }` with
   `the specimen '<folder>' ran past a pass cap (<passCap> loop passes, or <callDepthCap> entries of one function) on the input '<display>'. A prediction from a cut-off run would not be sound, so the specimen is refused. Give the loop or recursion a bound the derived inputs can reach.`
6. **Routes.** `routeGroupTransformer` (task 6.2.3). It keeps the first ordinary input for each arm combination and cause,
   and drops an edge input whose target the run never read, so a parameter that nothing reads owes no edge route.
7. **Dead arms.** `knownValueTraceTransformer` (task 6.1.6) on `routeGroup.unreachedArms`, with the stub correction
   from `plan.stubCorrection` or, for a stub companion, from the stub JSON in `files`. The first `refused` result
   makes this broker return `{ refused: <its sentence> }`. A `lint` result goes to the lint step, a `build-error`
   result to the admission step. The broker never predicts a lint because no input reached an arm.
8. **Report.** `fewestRunsCoverTransformer` (task 6.1.2) on the routes. `lintPredictTransformer` (task 6.2.5).
   `admissionPredictTransformer` (task 6.2.4). `branches` are the table's listed probes, sorted by file (`entry.ts`
   first, then the other files by path), line, then kind, each `{ file, kind, line, arms }` with its full arm list. `file` is the probe's `file` (a branch in `check-limit.ts` is reported with that file). `caseFailures` is `[]`. Parse with
   `specimenReportContract` (task 1.4.1).
9. **Today.** `todayMatchTransformer` (task 6.2.6) with `todayStatics.gaps`, the plan, the report, `routeGroup.causes`,
   the entry's parameter kinds, the write classes of the leaf variables and whether one comparison has two parameters as
   its operands, all from the generator's parse.
10. **Stub values.** `report.stubValues` holds one row per input task 1.4.1 says gets one (an environment
    variable, an object property, a whole parameter with an object member; never a scalar parameter or a scalar
    array element) that a leaf in the table reads, at the path task 1.4.1 defines (`options.label`, `items[].count`,
    `orders[].prices`, `SIZE`). Its `values` are the ordinary candidate values that input takes in the ordinary
    routes, one per arm, never an edge value (DESIGN.md decision "Derived stub values": one value that reaches
    every arm), written as TypeScript literal text, with `missing` and `unset` as task 1.4.1 says. A stub
    correction never changes these: they are what Assayer derives before a human corrects them, so
    `known/stub-correction` has `job.priority: ['5', '6']`. The card check compares them with each card's "Stub
    values Assayer derives" line, and the generated test compares them with Assayer's own stub index (DESIGN.md
    decision "Do generated tests compare derived stub values?").

A refused return never carries a partial report.

## Tests

The proxy needs nothing staged: the broker only runs transformers and the execute broker, and the sandbox is not I/O.
Render each specimen's `files` in the test from the card's code (written by hand). Assert the whole result with
`toStrictEqual`.

## What to implement

Three specimen tests assert an `unreachable-exit` lint. Update each one that a known value moves.

For each test file:

1. Read the specimen next to it, then the lint expectation in the test (it asserts the whole lint object: `rule`, `name`, `message`, `startLine`, `endLine`).
2. Decide by reading the specimen what makes the exit dead:
   - **A known value** (a welded `const`, a welded array length, a literal argument at a call site, an argument to an immediately-invoked function). The lint lands at the consumption point. Rewrite the expectation from the template in task 24.2.6: `startLine` and `endLine` are the line where the value enters (for a same-file `const`, the line where the branch reads it; for a call-site literal, the line of the call), `trace` lists `{ file: relPath, line }` steps from that line to the branch, and the message uses the new wording and gains its origin sentence. Work the lines out by reading the file.
   - **Contradicting guards** (no known value). The lint is unchanged: same message, same lines, no `trace` key. Leave the expectation as it is and say so in the reply.
3. Never copy the analyzer's output into the expectation. When the analyzer disagrees with what the template gives, report it as a bug.

If a core or app test also names one of these specimens and asserts its lint (for example `packages/core/src/brokers/run/unit/run-unit-broker.integration.test.ts`; the `detail-admissions.e2e.ts` row of `welded-arg` is task 24.6.2), list it in the reply instead of editing it (WORKER-BRIEF rule 4); the fan-out row 24.12 (`24.12-fan-out.md`) updates it.

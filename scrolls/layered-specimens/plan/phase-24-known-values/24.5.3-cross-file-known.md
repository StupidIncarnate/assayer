## The known-value record

Tasks of this phase share one record. It is a field of a condition leaf, `operandKnown` (contract: task 24.1.3):

```ts
operandKnown: {
  values: RepresentativeValue[];          // one or more; a ternary of literals gives two
  from: 'literal' | 'type';               // a literal in code or at a call site, or the operand's declared literal type
  origin: { line: number };               // the consumption point, a line in the file being analyzed
  hops: { file?: string; line: number }[];// each call or import step after the origin; `file` is absent for the file being analyzed
}
```

`operandConstValue` stays for the case of exactly one value, so the readers that exist today keep working. Every reader that takes a set reads `operandKnown`. The field is optional and absent when no known value reaches the leaf.

## What to implement

Card `known/env-two-files`: `env-two-files.ts` computes `limit = process.env.STRICT ? 5 : 10` and calls `applyLimit(limit)` from `apply-limit.ts`, which passes `limit` to `checkLimit` in `check-limit.ts`, which branches `limit > 20`.

1. For each call in the analyzed file whose argument is a known value (`literal` or `literal-set`, task 24.3.4) and whose callee is an `import` link, resolve the callee with `resolveSiblingCalleeBroker` (passing `importedName`).
2. In the callee file, build the callee function's request with a `KnownWeld` (imported from `contracts/known-weld/known-weld-contract.ts`, task 24.1.7) for the parameter: `origin` = the argument's `line` in the analyzed file, `hops` empty. Re-derive the callee's cases and unreachable exits with the existing derivation (`deriveCasesRequestTransformer` with `known`, task 24.4.1), so a dead arm in the callee is found, carrying `welded.known` (task 24.4.2).
3. When the callee passes the parameter straight on to a call of its own (`applyLimit` calls `checkLimit(limit)`), append a hop `{ file: <the callee file>, line: <that call's line> }` and repeat from step 1 for the next callee. Keep a seen-set of absolute file paths, so a cycle stops. Recursion only.
4. Each dead arm found this way becomes an `unreachable-exit` lint in **the analyzed file**, at the origin line (the call `applyLimit(limit)`), built by `unreachableLintTransformer` with `relPath` and `known` (task 24.2.6) and `welded.file` set to the file that holds the branch. `name` is the callee function that holds the dead arm (`checkLimit`). The trace holds `{ file: <analyzed file>, line: origin }`, then each hop, then `{ file: <file of the branch>, line: <branch line> }`. For the card the trace is `env-two-files.ts:5`, `apply-limit.ts:3`, `check-limit.ts:2`.
5. A callee that another caller can also reach with an unknown value is still flagged for this caller's known value: the known value is the consumption point's claim. Where no known value reaches a callee, nothing is flagged.
6. The callee's own file is not linted for the same arm: the lint belongs where the value enters.
7. The broker also passes `relPath` to `unreachableLintTransformer` at line 178 for its existing lints (guard contradictions), which build no trace.

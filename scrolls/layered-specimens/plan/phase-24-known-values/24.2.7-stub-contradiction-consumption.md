## What to implement

A stub correction is a known value: the values it gives a property are the only ones the property can take. When they rule out a guard's arm, the error lands where the correction enters the chain, the entry parameter whose type the correction covers, and it carries the path trace (DESIGN.md decision "Which channel reports a dead arm").

1. The transformer takes one more **optional** input, `consumers?`: for each corrected type key, the places a value of that type enters: `{ typeKey: string; relPath: string; line: number; hops: { file: string; line: number }[] }`, where `relPath` and `line` name the entry parameter and `hops` are the calls from that entry down to the file that holds the guard. Task 24.2.8 builds the list; task 24.3.3 passes it.
2. With a consumer for the error's type key, the error is reported on the consumer: `relPath` and `line` are the consumer's, `column` 1, and `trace` is `[{ file: <the overlay JSON path>, line: 1 }, { file: relPath, line }, ...hops, { file: <reader file>, line: <guard line> }]` (contract: tasks 23.1.5 and 24.1.6). The `reason` stays `contradicting-stub`.
3. The message keeps its words and gains the consumer: `` corrected values for property '<property>' cannot satisfy the guard at <reader>:<line> (needs <needs>), so the arm that guard protects can never run. The correction enters at <relPath>:<line> — rectify this stub ``. Tests assert it word for word.
4. Without a consumer (the input absent, or no entry for the type key), the error keeps today's location and message, and gets a one-step trace `[{ file: <overlay JSON path>, line: 1 }]`.
5. Card `known/stub-correction`: the correction gives `priority` only 1, 2 or 3; the guard `job.priority > 5` in `rank` needs 6 or more; `entry` takes `job: Job`, so the error is at `entry`'s parameter line (12), with trace `[Job.json line 1, entry line 12, line 10 (the call rank(job)), line 4 (the if)]`.

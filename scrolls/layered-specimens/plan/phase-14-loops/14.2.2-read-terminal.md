## What to implement

`read-terminal` answers "does this statement always stop the flow that follows it?". Inside a loop body, a `break`, a
`continue` and a labelled `break` or `continue` stop the flow that follows them in the body, so the statements after
`if (item > 2) { break; }` are guarded by the `else` arm. They do not leave the function, so nothing after the loop is
guarded by them.

1. A `break` statement, a `continue` statement and their labelled forms read as terminal (`true`). They only occur inside
   a loop body, a `switch` case or a labelled block, where stopping the following flow is exactly right.
2. A loop statement (`for`, `for…of`, `for…in`, `while`, `do…while`) never reads as terminal, even when its body always
   ends in `break`, `continue` or `return`: the loop may run zero times (and a `do…while` body may `continue` into the
   test), so the code after the loop is reachable. State this in the PURPOSE block.
3. `read-accounted` is unchanged: a loop is not accounted for, so a loop in tail position still owes the scope's end exit.
   Read it, confirm, and say so in your reply. If `read-accounted` needs a change for a `break`, stop and report it in
   `OPEN`: it is not one of this task's files.
4. A `return` stays terminal, as today.

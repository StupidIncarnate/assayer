# 10.3.1 Gate: the user decides each triage group

- **Phase:** 10, run the generated suite and triage. **Row:** #3, alone.
- **Depends on:** 10.2.1.
- **Model:** operator and user (no worker until the user has answered).
- **Covers:** PLAN.md "The loop".

## Files

| Action | Path | Folder type |
|---|---|---|
| edit | `scrolls/layered-specimens/TRIAGE-2.md` | plan document (markdown): each group's decision |

No worker is dispatched. Each decision that changes a file becomes a `10.4.<n>` task (`10.4-fan-out.md`).

## Steps

1. Stop the run and point the user at `scrolls/layered-specimens/TRIAGE-2.md`.
2. For each group the user decides one of these. Row 10.4 is a fan-out row: the operator records one task `10.4.<n>` per decision, each with at most 3 files, and dispatches them like any other row.
   - Generator wrong: a fix task `10.4.<n>` (opus) names the file. The fix regenerates the smoke repo and commits both together.
   - Known gap, `match` too narrow: a task `10.4.<n>` edits `today-statics.ts` and regenerates.
   - New Assayer gap: a task `10.4.<n>` adds the today row and regenerates. The core work goes into the phase the user names, or into a new phase after phase 27, written with README "The core phase template".
   - Closed gap: run the matching core phase's last task. It removes the row.
   - Refusal that looks wrong: a fix task `10.4.<n>` (opus) for the piece or the candidate-input rule.
3. Record each decision under its group in `TRIAGE-2.md`.
4. Run row 10.4, then rerun task 10.1.1 on the folders the fixes touched.

## Done when

Every group has a decision and a task, and a rerun of task 10.1.1 shows no failure that is not a closed gap.

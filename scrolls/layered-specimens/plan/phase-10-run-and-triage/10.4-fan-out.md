# 10.4 Fan-out: the fixes the triage gate decides

- **Phase:** 10, run the generated suite and triage. **Row:** #4, a fan-out row.
- **Depends on:** row #3 (10.3.1, the user's decision for each triage group).
- **Model:** opus for each `10.4.<n>` task that fixes the generator or a refusal (debugging work); the worker's default
  model for a task that only edits `today-statics.ts`.
- **Covers:** README "How the operator tells an expected failure from a regression", "The core phase template".

## How the fan-out works

This file is the one definition of row 10.4. There is no task `10.4` itself. Task 10.3.1 records the user's decision
for each group of `TRIAGE-2.md`.

1. For each decision that changes a file, the operator writes a real task file,
   `phase-10-run-and-triage/10.4.<n>-<slug>.md`, in the format of every other task file: the id, the phase, the row,
   `Depends on: 10.3.1`, a Files table of 1 to 3 files, what to change and why (the decision, quoted), the commands
   below, and "Done when". It adds the ids to the README tracker row before it dispatches them.
2. No two tasks of the row edit one file. Every task that edits `today-statics.ts` is one task, so the operator merges
   those decisions into it.
3. A decision that adds a core phase is not a task of this row: the operator writes the new phase with README "The core
   phase template" and adds it to the tracker after phase 27.
4. A task that changes the generator or `today-statics.ts` regenerates the smoke repo; the operator commits the change
   and the regenerated output together.


Every command exits 0, and each folder the decision named passes.

## What to implement

1. **Move.** The analyzer reads the enum member, so the file admits nothing. It lives under `happy-path/switch/`, and the
   folder and files are named `enum-cases`.
2. **Specimen.** Keep the code (a string enum `Severity` with `Low` and `High`, and `rank` switching on it with `case
   Severity.Low` and a `default`). If the file has a header comment, rewrite it to describe an enum member the analyzer reads.
3. **Test.** Rewrite it for what the file does, with the layout of `happy-path/switch/in-function/in-function.test.ts`.
   Write the expected values by reasoning from the design. Assert:
   - the analysis has one function, `rank`, with one `switch` branch whose arms are `case:low` and `default`, and no entry in
     `undriven`, `gaps`, `darkSpots` or `lints`;
   - the case on `Severity.Low` reads as an equality on the member's value `'low'` (the leaf's predicate is `eq` with `'low'`);
   - the every-route set holds two driven cases, one reaching the `Low` exit and one the `default` exit.
4. **Registry.** Delete the old key `sad-path/undriven/enum-case/enum-case.ts`, and add:

   ```ts
   [`${CATALOGUE}/happy-path/switch/enum-cases/enum-cases.ts`]: ['access:named', 'branch:switch', 'param:union'],
   ```

   Declare the traits by reading the file: an enum parameter is read as a union of its members.
5. Probe first (`packages/core/CLAUDE.md` section 7). If the enum parameter is not read as a union of its members, or the case
   is not steerable, that is a defect in tasks 19.1.1 or 19.2.1: report what the probe shows and do not paper over it.

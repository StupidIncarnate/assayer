## What to implement

**Promise callbacks.** Today `ITERATION_METHODS` names the array methods whose callback is driven, and any other callback
is undriven (`CALLBACK_UNDRIVEN_REASON`). Add a second route for a callback passed to a call whose `method` is `then`,
`catch` or `finally`:

1. From that call site, walk `receiverPosition` through the host's `calls` to the root of the chain: a call site that
   has no `receiverPosition`, or whose method is not `then`, `catch` or `finally`.
2. The root decides the receiver:
   - a call with `receiver` `Promise` and `method` `resolve` is `{ kind: 'resolves', value: <its first argument> }`. The
     name `Promise` is the one convention the call site can offer; say so in a comment;
   - a call whose callee is `local` and resolves to a scope of this file is `{ kind: 'call', callee: <that scope>, args }`;
   - anything else leaves the callback undriven with the existing reason.
3. Drive it only when the host is branchless with one exit and the root call's `guardPath` is empty. A branching host is a
   later increment, as it is for array callbacks.
4. Call `throughSettleCasesTransformer` and add its analysis to `followedEntries` as a `through-caller` entry named for the
   callback. Add its `unfillable` entries to `refusals` with the host as owner.
5. A promise callback is followed even when it has no branch of its own, because its settle arms are the branch: a branchless
   `.catch(() => 'failed')` on a receiver that can reject yields an entry. A `.finally` callback has no arm and is not
   followed unless it has a branch. The existing rule "the trigger is always a branch" stays for everything else.

**Executors.** A scope whose record carries `executor: true` (tasks 17.1.2 and 17.2.1) runs in place when its host runs, and reads the
host's parameters by closure. Drive it through the host:

1. The host is the reachable scope whose `calls` or nested scopes contain it. Find it the way the file finds the host of a
   callback (the scope whose start and end lines enclose the executor's).
2. Derive the executor's cases with `deriveCasesTransformer` over the **host's** parameters (`appliedParamsTransformer`), the
   executor's branches and exits, `envDrivable: false`, no harness. Build the request with
   `deriveCasesRequestTransformer` as `throughCallbackCasesTransformer` does.
3. The entry keeps the executor's identity (name, scope path, exits) with access `through-caller`, `callerName` the host's
   name, params the host's. This is the executor's twin of the IIFE route, which is driven by the module instead.
4. An executor whose host has a parameter the fill seam refuses reports the refusal against the host, like every other
   route.

Update the header comment (the list of ways a private is reached gains the two routes).

## Tests

- `VALID: card callback/then (host entry(count) returning Promise.resolve(count).then(cb)) => the callback is followed as a through-caller entry with the ternary's two arms, no settles step`
- `VALID: card callback/then-catch-finally => the .then callback, the branchless .catch callback and the .finally callback with its ternary-free body; the .finally callback yields no entry`
- `VALID: the .catch callback entry carries settles:runs and settles:skipped`
- `VALID: a chain a.then(b).catch(c) => both callbacks reach the same root receiver`
- `VALID: card promise/alone => the executor is followed as a through-caller entry named for the executor, over the host's parameter count, with if arms then and else`
- `INVALID: .then on a receiver that is not Promise.resolve and not a same-file call => the callback stays undriven with the existing reason`
- `INVALID: a branching host => the callback stays undriven`
- `INVALID: a root call behind a guard => the callback stays undriven`
- `EDGE: an executor whose host has a parameter the fill seam refuses => a refusal against the host`
- `EDGE: array callbacks (map, filter) still drive exactly as before`

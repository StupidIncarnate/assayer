## What to implement

1. The specimen holds the card's code with a named entry:

   ```ts
   export const checkSize = (count: number): Promise<string> =>
     new Promise((resolve, reject) => {
       if (count > 2) {
         resolve('big');
         return;
       }
       reject(new Error('too small'));
     });
   ```

2. The test asserts what is bespoke to this file. Write every expected value by reasoning from the card.
   - the executor is a `through-caller` entry named for the arrow, driven through `checkSize`, with one `if` (arms `then`,
     `else`) that reads `count`, the host's parameter, by closure;
   - five cases per the card: `count` 3 takes `then` (the executor resolves), and `count` 2, 0, `NaN` and -1 take `else` (it
     rejects); the fewest-runs set holds 2 cases, one of each arm;
   - `resolve` and `reject` are ordinary calls and mint no exit (task 17.2.2). The executor's exits are its `return;` and the
     end of its body;
   - no dark spot, no undriven entry, no gap and no lint.
3. **Bucket.** The four rejecting cases end with a rejected promise after the executor reached its exit. Task 17.1.4 makes
   the interpreter judge such a case by that exit, so the run passes them and the file sits under `happy-path/`.
   `run-unit-broker.integration.test.ts` checks it.
4. Registry: add one line, declared by reading the file. Expect `access:named`, `access:through-caller` and `branch:if`.
5. Probe first and check formatting immunity as in task 16.5.1. A difference between a probe and the card is a bug to report.

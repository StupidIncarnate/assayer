## Words used here

An **executor** is the function passed as the first argument of `new Promise(...)`. The language calls it in place, with
two functions: `resolve` and `reject`. It runs when the host that evaluates `new Promise` runs, and it reads the host's
parameters by closure, so the executor's branches are decided by the host's parameters, never by the executor's own.

## What to implement

1. **Recognise it.** In `handle-function`, an arrow function or function expression is an executor when its parent is a
   `NewExpression`, the function is that expression's first argument, and the expression's callee is the identifier `Promise`
   that resolves to the global (no declaration of the name in this source file). Read the parent through the node's own
   `getParent()` once: this is a local property of the function node, not context.
2. **Record it.** An executor's scope record carries `executor: true`. Everything else about the scope is unchanged: it still
   opens its own scope, so a `return;` inside it is an exit of the executor and never of its host. Its parameters are read as
   for any function, so `resolve` and `reject` arrive as callable parameters.
3. **The body reads the host's parameters.** Build the context of an executor's body with `params: context.params`, the host's
   parameters, through `walkContextTransformer`, so `count` in `if (count > 2)` reads as the host's parameter with its declared
   type. The scope record keeps the executor's own parameters (`resolve`, `reject`). This is the rule task 15.4.3 applies to a
   returned closure.
4. A function that is not an executor reads exactly as before. A `new Promise` whose argument is a named function reference is
   not an executor here.
5. Header comment: the field, why the executor keeps its own scope, and the host-parameter rule.

Task 17.2.2 records that the calls to `resolve` and `reject` mint no exit, and task 17.3.1 makes `follow-calls` drive an executor
through its host.

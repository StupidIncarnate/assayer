## What to implement

1. **Chain facts.** Today a call records `receiver` and `method` only when its receiver is a plain identifier. Record `method`
   (the property name) for every call whose callee is a property access, whatever the receiver. Record `receiver` only for a
   plain identifier receiver, as before. When the receiver, after removing parentheses, is itself a call expression, record
   `receiverPosition` as the line and column of that call, computed the same way the call's own `position` is
   (`getLineAndColumnAtPos(node.getStart())`), so the two coordinates match. A call whose receiver is not a call leaves
   `receiverPosition` absent. Read the property name from the node, never from text.
2. **`resolve` and `reject` calls mint no exit.** The README names them exits, and the executor's own exits already stand for
   them: a `return;` inside the executor and the end of its body are exits of the executor scope (task 17.1.2 keeps the
   executor a scope of its own), and the call that precedes either is not a second one. A call to `resolve` or `reject` that
   also minted an exit would collide with the `return;` that usually follows it. Both would carry the same kind and the same
   guard path, so one coverage id would name two exits, and two exits of one guard length leave a route with no single exit to
   reach. So these calls stay ordinary call sites, and this decision goes in the handler's header comment. The settle
   outcome of an executor route is not compared by anything, and the interpreter judges the case by the exit it reaches.
3. Header comment: the new facts and the decision in step 2.

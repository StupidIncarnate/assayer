# P0-5: wiring that `dungeonmaster init` does not do

## Goal

Every package builds, typechecks and tests the way `dungeonmaster create-package` lays a package out: `node16`
resolution with the `source` condition, no `composite`, no `references`, and one `tsconfig.build.json` per tsc
package. One script builds every workspace package, the four gateways included, in dependency order. Jest, ESLint and
each `package.json` are wired to the gateways, so Phase G and Phase M start from a tree whose reds are real.

## Findings

Every fact below was read from disk on 2026-09-30. "The scaffold" means what `create-package` would write for a
package's type. `create-package --dry-run` wrote nothing (checked with `git status --porcelain` before and after
six dry runs). It prints only file NAMES, never contents. So the contents were rendered by calling the same pure
function the command calls, `packageScaffoldFilesTransformer`, from
`node_modules/@dungeonmaster/cli/dist/src/transformers/package-scaffold-files/package-scaffold-files-transformer.js`,
with `usesPublishedJestBase: false`. That is the value the command computes for assayer, because assayer has a
repo-root `jest.config.base.js`. The gateways were rendered the same way through
`gatewayPackageScaffoldFilesTransformer`. The renders are in the planner's scratchpad, not in the repo.

Package types come from `get-project-map`: `app` is `frontend-react`, `cli` is `cli-tool`, and `core`, `desktop`,
`shared` and `hydration-recipes` are `library`.

### (a) Each package's configs against the scaffold

**The gateways match.** All four gateways' `package.json`, `tsconfig.json`, `tsconfig.build.json` and `jest.config.js`
are byte-identical to the gateway scaffold. The one difference is expected: `@assayer/npm` carries the
`dependencies` that `gateway-sync` added, and its placeholder `src/index.d.ts` is gone. Nothing in a gateway changes
in this item, except the react folder in part (e). The gateway typecheck is green apart from that folder (run
`1790828510620-0722`: bin, node and browser PASS; npm has 8 TS2305 errors, all in `src/react/react.ts`).

**The root `tsconfig.json`** carries `"composite": false` and a `references` array naming shared, core, desktop and
cli. The architecture says no config sets `composite` and none carries `references`. Both keys go. Everything else
stays: `noEmit`, `jsx`, `lib` (with `DOM`), `allowJs`, `typeRoots`, `module`/`moduleResolution` `node16`,
`customConditions: ["source"]`, `include`, and `extends: "./tsconfig.base.json"`.

**The root `tsconfig.build.json`** holds only a `references` array. It exists for `tsc --build`. Part (b) replaces
that build, so this file moves to `tmp/deletions/P0-5/tsconfig.build.json`.

**`tsconfig.base.json`** still says `module: commonjs` and `moduleResolution: node`. Packages stop extending it
directly; they extend the root `tsconfig.json`, which overrides both to `node16`. The base file itself does not change.

**Library packages: `shared`, `core`, `desktop`.** Each `tsconfig.json` today extends `../../tsconfig.base.json`
(so it resolves with `node`, which ignores `exports` and `imports`) and sets `composite: true`, `rootDir`, `outDir`
and `tsBuildInfoFile`. Core and desktop also carry `references`. The scaffold `tsconfig.json` is:

**`scripts/jest-global-setup.js` needs a temporary change. Doing nothing is not an option**, for two reasons:

1. Its one build step runs `tsc --build tsconfig.build.json`. Once part (a) drops `composite` and that file moves out,
   the step fails (TS6306, "Referenced project must have setting composite: true", or a missing file), and every Jest
   run aborts before its first test. Change the step to `node scripts/build-workspaces.mjs --tsc-only`, then keep the
   copy step. The thrown P1 message names the failing step by its label, so the label changes with it, and the
   message's line "To reproduce this step alone" prints the new command.
2. Part (c) spreads the published Jest base, which brings its own `globalSetup` (the home sandbox) and
   `globalTeardown`. Jest takes one `globalSetup`. If assayer's build setup simply replaces the sandbox setup, the
   published teardown still runs, and its `finally` block calls `rmSync(process.env.HOME, { recursive: true, force:
   true })` (`node_modules/@dungeonmaster/testing/src/jest.setup-global-teardown.js` lines 67-70). With no sandbox,
   `HOME` is the developer's real home directory. So after its build steps, `jest-global-setup.js` must call the
   published sandbox setup: `require(join(repoRoot, 'node_modules/@dungeonmaster/testing/src/jest.setup-global.js'))()`.

P0-5b still removes this file. After P0-5, "drop `globalSetup`" in P0-5b means deleting assayer's override line, so
the published sandbox setup applies on its own. P0-5b must keep the published `globalTeardown`.

## Decisions for the operator

1. **The Jest `globalSetup` chain (part b).** Recommended: `jest-global-setup.js` builds, then calls the published
   sandbox setup, until P0-5b deletes it. The alternative is to take P0-5b's "no build before tests" now. That moves
   P0-5b's probes into this item, so it is not recommended.
2. **Gateway `jest.config.js`.** Recommended: leave them as `init` writes them. They spread the published base, which
   has no `source` condition, so a gateway test that imports another gateway (browser imports node) reads that
   gateway's `dist`. Switching them to the root base would make them differ from the generator, and browser's config
   pins `testEnvironmentOptions`. Report it upstream (U-5) instead.
3. **`--tsc-only` in `build-workspaces.mjs`.** It is the one flag the port adds. Recommended, so a Jest run does not
   pay for a Vite build until P0-5b removes the build.
4. **The root `lib` keeps `DOM`.** Shared, core and cli gain DOM types through `extends: ../../tsconfig.json`.
   Recommended: keep it in this item. Changing the root `lib` also changes what the main ESLint block's typed rules see
   in app files.

## Risks

- **The real home directory.** If the published `globalTeardown` ever runs without the published `globalSetup`, it
  deletes `$HOME` recursively. Batch 9 must not land before Batch 7, and P0-5b must keep both published entries
  together. This is the most dangerous step in the item.
- **Between Batch 1 and Batch 7, every Jest run aborts**, because `jest-global-setup.js` still runs `tsc --build`.
  Run no unit or integration check in that window. The operator should run Batches 1 to 7 back to back.
- **More visible reds, all of them real.** Packages move from `node` to `node16` resolution, so TS2307 errors turn
  into the errors they hid: missing names (P0-6), `AdapterResult` (Phase A), implicit `any`. App moves from `dist`
  declarations to source. That is the point of the item, but the operator should record before and after counts.
- **Ward's typecheck merges `tsconfig.build.json`**, whose `gateway-dist` condition reads gateway types from `dist`.
  From Batch 3 on, typecheck needs built gateways. Rebuild the gateways after every Phase G item, as the EPIC says.
- **The published base changes test behaviour.** ts-jest `diagnostics` goes off, so a type error no longer fails a
  test; ward's typecheck still does. MSW loads in every package. `transformIgnorePatterns: []` lets ts-jest transform
  ESM inside `node_modules`, which makes a cold first run slower.
- **`allowJs` from the root tsconfig.** Packages now inherit `allowJs: true`. A `.ts` file that imports one of core's
  root `.js` files (`probe-runtime.js`, `probe-transformer.js`, `harness-registrar.js`) would pull it into the
  program and emit it. Batch 1's typecheck shows whether any does.
- **The prune deletes stale emit.** The first `build:clean` removes old `dist/.tsbuildinfo` files and core's
  `dist/test/`. Nothing reads them. Hydration-recipes' old `dist/index.js` moves to `dist/src/index.js`.
- **Lint on gateway files.** Batch 10 turns on the gateway block, including `gateway-colocation` with
  `requireStub`. Gateway files that `gateway-sync` wrote may report new errors, and `--fix` may rewrite them. R-2
  scans these to 0; this item only records the counts.
- **Conflicts with P0-5b.** P0-5b's file list includes `jest.config.base.js`, which this item rewrites whole. Its
  "drop `globalSetup`" becomes "delete assayer's `globalSetup` override line". P0-5b also moves
  `scripts/jest-global-setup.js`, which this item edits; nothing else imports it. P0-5b's nested Jest config needs
  `customExportConditions` with `source`, the same list this item puts in the root base, so the two agree. P0-5b's
  planner reads this item's diff first.

## Upstream reports found while planning

- **U-1.** `create-package --dry-run` prints file names only. A consumer cannot diff a package against the scaffold
  without calling `packageScaffoldFilesTransformer` directly.
- **U-2.** `create-package` treats any repo with a repo-root `jest.config.base.js` as the dungeonmaster monorepo. For
  `cli-tool` and `frontend-react` it then writes a `jest.config.js` that requires
  `../../packages/testing/ts-jest/options.js`, which does not exist in a consumer.
- **U-3.** The published `jest.setup-global-teardown.js` removes `process.env.HOME` in a `finally` block even when its
  own `globalSetup` never ran. A consumer that replaces the base's `globalSetup` loses its real home directory on the
  first Jest run.
- **U-4.** `configGatewayLintConfigBroker` and `configWorkspacePackageNamesBroker` are not reachable through the
  eslint plugin's `exports`. A consumer must require them from `dist` by absolute path.
- **U-5.** `init` writes gateway `jest.config.js` files that spread the published base. In a monorepo, a gateway test
  that imports a sibling gateway then reads that sibling's `dist`, not its source.

# G-2: `#gateway/node/vm`

## What core calls today

Core has one `vm` caller: `packages/core/src/adapters/typescript/load-harness/typescript-load-harness-adapter.ts`.
It imports `createContext` and `runInContext` from `node:vm`. It calls them once each:

- `createContext(sandbox)`, where `sandbox` is a plain object holding a CommonJS shell (`module`, `exports`) and a
  `require` that hands back only `assayerHarness`.
- `runInContext(transpiled.outputText, context, { filename: fileName })`.

It also calls `types.isNativeError` from `node:util`. `#gateway/node/util` already re-exports all of `util`, so this
item adds nothing for it.

## Plan

One batch, one agent. The node gateway's `package.json` already maps `./*` to `./src/*/*.ts`, so
`#gateway/node/vm` resolves to `src/vm/vm.ts` with no `exports` edit.

| File | What |
|---|---|
| `packages/@gateway/node/src/vm/vm.ts` | Pass-through. Re-exports `createContext` and `runInContext` from `vm` by name, and nothing else. |
| `packages/@gateway/node/src/vm/vm.test.ts` | Proves each name is the same binding `vm` provides, and that code run in a context made through the gateway reaches no host global and no gateway import. |

No proxy and no stub. Both calls are pure re-exports with no body of their own, so they run real. Core's harness
loader exists to evaluate the harness; a test that replaced `runInContext` would prove nothing about it. Evaluating a
string in a fresh context does no I/O, so the I/O trap does not catch it either.

The code that runs INSIDE the sandbox never imports a gateway. Its only `require` is the one core hands to
`createContext`, and the gateway adds nothing to the context. `vm.test.ts` checks the second half.

Out of scope: rewiring the core adapter to `#gateway/node/vm`. Phase A (or M-1's codemod) does that.

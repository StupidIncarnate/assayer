### A. Zod 4 message text: 94 unit files, 175 tests

**Cause.** Contract tests assert zod 3's error text with `toThrow(/.../u)`. Zod 4.6.5 words every message
differently. Commit `b8378b7` fixed app's five tests the same way.

**Evidence.** `packages/cli/src/contracts/cli-run-result/cli-run-result-contract.test.ts:31`:
`}).toThrow(/[Ee]xpected integer/u);` receives
`"message": "Invalid input: expected int, received number"`. Every file in the cluster has the same shape: an
`Expected pattern` line and a `Received message` that is a zod 4 issue array. The pairs seen in the run:

| zod 3 pattern in the test | zod 4 message received | tests |
|---|---|---|
| `/Required/u` | `Invalid input: expected <type>, received undefined` (array 51, string 30, object 8, boolean 2, number 1) | 92 |
| `/at least 1 character/u`, `/at least 1/u` | `Too small: expected string to have >=1 characters` | 48 |
| `/Expected string/u` | `Invalid input: expected string, received number` | 10 |
| `/greater than 0/u` | `Too small: expected number to be >0` | 8 |
| `/greater than or equal to 0/u` | `Too small: expected number to be >=0` | 4 |
| `/integer/u`, `/Expected integer/u`, `/[Ee]xpected integer/u` | `Invalid input: expected int, received number` | 6 |
| `/Expected object/u`, `/Expected boolean/u`, `/Expected number/u`, `/Expected array/u` | `Invalid input: expected <type>, received <type>` | 6 |
| `/Invalid option: expected one of/u` | `Invalid input: expected \"unhandled-syntax\"` (a one-member enum) | 1 |

The `/Required/u` row shows why a fixed text map cannot do this: the new text names the expected type, and only the
received message says which type it is.

**Files.** shared 58, core 23, cli 7, desktop 6. The list is in Appendix A. One of them,
`packages/desktop/src/adapters/electron/preload-bridge/reply-value-layer-adapter.test.ts`, sits in `adapters/`. Phase
A's A-2 moves it with its body unchanged, so its assertion is still wrong after the move. Fix it here.

**Fix: script-able.** One script, in `$H/scripts/p0-9-zod4-messages/`:

1. Read `npm run ward -- detail 1790832052277-4919` (or a fresh scoped run's detail) and split it into failing tests.
2. For each test with an `Expected pattern:` line and a `Received message: "[` line, take the first issue's
   `message` value.
3. Take the stack frame in the test file itself whose line holds `.toThrow(`. In the run this is the last
   `at Object.<anonymous> (<abs test path>:<line>:<col>)` frame naming the test file.
4. On that line, replace the regex literal inside `.toThrow(...)` with `/<message, regex-escaped>/u`. Keep the
   assertion unanchored, as `b8378b7` did for app.
5. Write a leftovers file for every test where the line holds no regex literal (a shared constant, an `it.each`
   table) or where two tests on one line need different text.

Gate: `npm run ward -- --only unit -- <files>` per package. Expect 0 leftovers or a handful.

Phase B's W1 and W5 waves later turn many standalone scalar contracts plain or into fields, and some of these test
files go with them. That is not double work: this script is one pass, and the tree needs these tests green through
Phases G to C.

### C. The `source` condition leaks into the built CLI: 2 integration files, 25 tests

**Cause.** Ward starts Jest with `NODE_OPTIONS=--conditions=source`. The CLI test harness spawns the built CLI with
`spawn(process.execPath, [cliEntry, ...argv], { cwd: dir, ... })` and no `env`, so the child inherits the real
`NODE_OPTIONS`. With the `source` condition, the built CLI resolves `#gateway/node/process` to the gateway's
TypeScript source, and Node cannot load it.

**Evidence.**

- Every failing test's stderr: `Error [ERR_MODULE_NOT_FOUND]: Cannot find module
  '/home/brutus-home/projects/assayer/packages/@gateway/node/src/process/argv/argv' imported from
  /home/brutus-home/projects/assayer/packages/@gateway/node/src/process/process.ts`.
- Probe: `node packages/cli/dist/bin/assayer.js version` prints `assayer 1.0.0` and exits 0. The same command with
  `NODE_OPTIONS=--conditions=source` fails with the error above.
- Ward sets the variable at
  `codex-of-consentient-craft/packages/ward/src/brokers/check-run/integration/check-run-integration-broker.ts:196`:
  `...(sourceConditionSupportedBroker({ cwd }) ? { NODE_OPTIONS: '--conditions=source' } : {}),`. The unit and e2e
  brokers do the same (`check-run-unit-broker.ts:207`, `check-run-e2e-broker.ts:190`).
- Dungeonmaster's `packages/testing/src/jest.setup.js:15` strips the flag from `process.env`, and its comment says
  this keeps it out of every process a test spawns. It cannot. Inside a test file `process.env` is Jest's sandbox copy
  (`jest-util`'s `createProcessEnv` returns `Object.assign(proxy, process.env)`). Node's `spawn` with no `env` option
  reads the real environment, which still holds the flag. The strip only helps a spawn that passes
  `env: { ...process.env }` explicitly.

**Files.** `packages/cli/bin/assayer.integration.test.ts` (24 tests) and
`packages/cli/src/flows/assayer/assayer-flow.integration.test.ts` (1 test). Both use
`packages/cli/test/harnesses/assayer-cli.harness.ts:64`. The build at `b8378b7` is current: the probe above runs that
build clean.

**Fix: hand work in dungeonmaster (needs judgement).** Ward hands Jest and Playwright the condition as a Node
`execArgv` (`node --conditions=source <runner bin>`) instead of through `NODE_OPTIONS`. Jest's workers and
Playwright's workers are forked, and a fork inherits `execArgv` by default, so tests still read source. A test's own
`spawn(process.execPath, ...)` does not inherit `execArgv`, so a built child stays built. The `jest.setup.js` strip and
its comment then go. The dungeonmaster agent must run dungeonmaster's own integration and e2e suites after this,
because any dungeonmaster test that leaned on the leaked flag shows up there. Fallback, if that cannot land: each
assayer harness that spawns a built binary passes an `env` without `--conditions=source`. That is a local workaround,
so it needs a concession row. The harnesses are `assayer-cli.harness.ts`, `assayer-compile.harness.ts`,
`smoke-cache.harness.ts` and the five Electron launch harnesses in `packages/app/test/harnesses/`.

### D. The I/O trap refuses ts-morph's own file reads: 2 unit files, 17 tests

**Cause.** The published I/O trap lets a READ through when the TypeScript compiler makes it. It recognises the
compiler only by the frame pattern `/[\\/]node_modules[\\/]typescript[\\/]/u`
(`codex-of-consentient-craft/packages/testing/src/jest.setup-io-trap.js:99`). ts-morph ships its own copy of the
compiler and its own file system host in `@ts-morph/common`, so its reads match nothing and the trap throws.

**Evidence.** `ts-morph-read-external-signature-adapter.test.ts`, first test:
`[io-trap] unstaged fs.readFileSync("/tmp/assayer-extsig-ForZZF/tsconfig.json")`, nearest frame
`at NodeRuntimeFileSystem.readFileSync (/home/brutus-home/projects/assayer/node_modules/@ts-morph/common/dist/ts-morph-common.js:1308:30)`,
reached from `new Project` at `ts-morph-read-external-signature-adapter.ts:40`. The global-signature adapter fails the
same way at its line 61.

**Files.** `packages/core/src/adapters/ts-morph/read-external-signature/ts-morph-read-external-signature-adapter.test.ts`
(10 tests) and `packages/core/src/adapters/ts-morph/read-global-signature/ts-morph-read-global-signature-adapter.test.ts`
(7 tests).

**Fix: hand work in dungeonmaster.** Widen `TYPESCRIPT_COMPILER_FRAME` to also match `node_modules/@ts-morph/common/`.
ts-morph's reads are TypeScript compiler reads, so the trap's own rule ("a real TypeScript compile runs fully real")
already covers them. Add a test in the testing package. Phase A's A-2 later moves these two adapters with bodies
unchanged (census group CG12), and the tests keep passing through the move. The alternative, moving both tests to
`.integration.test.ts`, conflicts with the rule that integration tests are for startup files and flows only.

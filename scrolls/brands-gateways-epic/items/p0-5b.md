# P0-5b: remove the build before tests (D10)

## Goal

Assayer's Jest runs stop building the repo before they start. The wrapped runner (the nested Jest that
`runUnitBroker` starts in-process) loads core's runtime modules from the same tree its broker was loaded from:
TypeScript source when the broker runs from `src`, and compiled output when it runs from `dist`. A unit run or a
core integration run then needs no build, and `src` and `dist` can no longer disagree inside one run.

## Probes

Each probe was answered by reading code on 2026-09-30, not by running Jest.

### (a) Does ts-jest load `probe-transformer.js` inside the outer Jest sandbox?

**Answer: yes.** When a core test drives the runner, the nested Jest is itself a module the outer Jest loaded. So
the nested ts-jest's `require` is the outer Jest runtime's `require`, and `probe-transformer.js` plus everything it
requires load inside the outer sandbox. They go through the outer config's resolver, transforms and export
conditions. Outside Jest, for example the built CLI, plain Node loads the same file.

Evidence:

- `packages/core/test/harnesses/run-unit.harness.ts:31` — "import { runUnitBroker } from '../../src/brokers/run/unit/run-unit-broker';" — the integration harness calls the broker in-process, from source.
- `packages/core/src/adapters/jest/run-cli/jest-run-cli-adapter.ts:31` — "import { runCLI } from '@jest/core';" — the nested Jest is an ordinary import, so the outer Jest loads it.
- `packages/core/src/adapters/jest/run-cli/jest-run-cli-adapter.ts:80` — "const { results } = await runCLI(" — no child process; the nested Jest runs in the same process.
- `node_modules/jest-runtime/build/index.js:1237` — "value: this._createRequireImplementation(module, options)" — every module the outer Jest loads gets the outer runtime's `require`.
- `node_modules/@jest/transform/build/index.js:260` — "let transformer = await (0, _jestUtil().requireOrImportModule)(transformPath);" — the nested Jest loads `ts-jest` this way.
- `node_modules/jest-util/build/index.js:1010` — "const requiredModule = require(filePath);" — that `require` is the outer runtime's, because `jest-util` itself was loaded by the outer Jest.
- `node_modules/ts-jest/dist/legacy/config/config-set.js:350` — "transformerFunc = require(transformerPath);" — ts-jest loads an AST transformer with its own module's `require`.

What the implementation must do:

- `probe-transformer.js` may `require` a `.ts` file only in source mode. That is always safe. Source mode exists only
  when the broker itself was loaded as `.ts`, so the process already has a TypeScript loader: the outer ts-jest in a
  test, or `tsx` from a command line.
- `probe-transformer.js` reads the probe-inject module's path from its ts-jest `options`, and requires it inside
  `factory`, not at module top. ts-jest hands `options` only to `factory`.
- Nothing changes about which sandbox loads the file. Today the same file loads `dist/adapters` in the same outer
  sandbox.

### (b) Do core source's `#gateway/*` imports resolve under the nested Jest?

**Answer: there are none today, and they will resolve once Phase M adds them, provided the nested config sets the
`source` export condition.** Without that condition they resolve to the gateway's `dist`, which needs a build.

Evidence:

- `packages/core/package.json:56` — "\"#gateway/npm/*\": \"@assayer/npm/*\"," — core's `imports` map sends `#gateway/npm/*` to the npm gateway package.
- `node_modules/jest-resolve/build/index.js:163` — "conditionNames: conditionNames || conditions || ['require', 'node', 'default']," — Jest 30's resolver (`unrs-resolver`) honors `imports` and `exports` maps and takes Jest's export conditions as its condition list.
- `node_modules/jest-runtime/build/index.js:392` — "this.cjsConditions = [...new Set(['require', 'node', 'default', ...envExportConditions])];" — the environment's conditions are added to `require`, `node` and `default`.
- `packages/@gateway/npm/package.json:33` — "\"source\": \"./src/*/*.ts\"," — under the `./*` key (line 30), `source` comes first and names TypeScript source.
- `packages/@gateway/npm/package.json:36` — "\"require\": \"./dist/*/*.js\"" — without `source`, the same key resolves to `dist`.

What the implementation must do:

- In source mode, the nested config sets `testEnvironmentOptions.customExportConditions` to
  `['source', 'node', 'node-addons']`. That is Jest's node default (`node_modules/jest-environment-node/build/index.js:93`

- In `dist` mode, the nested config sets no `testEnvironmentOptions`. A published core ships `dist` only. A `source`

- The nested config gets no gateway module-mock resolver. The nested run executes the consumer's real code, so a
  `.jest-mock.cjs` must not replace anything there.

## Design

### Terms

- **Core root**: the folder holding `probe-runtime.js`. `run-paths-broker` already finds it by walking up from its
  own `__dirname` (`run-paths-broker.ts:33`). The run-unit harness passes it directly.
- **Tree**: `'source'` or `'dist'`. It says which copy of core's runtime modules the nested Jest loads.
- **Runtime modules**: the four typed modules that run inside the nested Jest, plus `assayerHarness`.
  - `jestInterpretCaseAdapter` and `jestResolveEntryAdapter`, which the shim calls.
  - `jestProbeRuntimeAdapter`, which `probe-runtime.js` installs as `__P`.
  - `jestProbeInjectAdapter`, which `probe-transformer.js` calls.
  - `assayerHarness`, which `harness-registrar.js` calls, from core's main barrel `index`.
- **Ceremony files**: the three plain-JS files at the core root (`probe-runtime.js`, `probe-transformer.js`,
  `harness-registrar.js`). Jest needs each one as a file path. They stay plain JS at the core root in both trees.

### How the broker picks the tree

`runUnitBroker` decides, because it is the one broker every run passes through, including the run-unit harness
that skips `run-paths-broker`. It calls a new pure transformer with its own location:

```ts
const runtime = coreRuntimeTransformer({ coreRoot, loadedFrom: __dirname });
```

`coreRuntimeTransformer` returns `tree: 'dist'` when `loadedFrom` is `${coreRoot}/dist` or starts with
`${coreRoot}/dist/`. Otherwise it returns `tree: 'source'`. The `/` after `dist` keeps a folder such as `distant`
from counting. It uses string templates, not `node:path`, because a transformer may not import an outside package.
Assayer already builds cache paths with `/` templates (`run-unit-broker.ts:115`).

The cases:

| Where `runUnitBroker` was loaded from | `__dirname` | Tree |
|---|---|---|
| A core test, through ts-jest | `<repo>/packages/core/src/brokers/run/unit` | source |
| `tsx packages/cli/bin/assayer.ts` | the same | source |
| The built CLI, `npm run dev`, the desktop's CLI child | `<repo>/packages/core/dist/src/brokers/run/unit` | dist |
| A consumer's install | `<consumer>/node_modules/@assayer/core/dist/src/brokers/run/unit` | dist |

No environment variable and no `existsSync` takes part. The answer is a pure function of two strings, so a unit
test covers both trees.

`run-paths-broker.ts` and `run-each-layer-broker.ts` keep their code. They pass `coreRoot` through, as they do now.
This departs from the EPIC row, which put the choice in those two files. The harness calls `runUnitBroker`
directly, so a choice made higher up would need the harness to repeat it.

### The runtime description

`coreRuntimeTransformer` returns a `CoreRuntime` object. Every field except `tree` is an absolute path and reuses
`filePathContract` from `packages/core/src/contracts/file-path/file-path-contract.ts`.

| Field | Source tree | `dist` tree |
|---|---|---|
| `tree` | `'source'` | `'dist'` |
| `setupFile` | `<coreRoot>/probe-runtime.js` | the same |
| `astTransformer` | `<coreRoot>/probe-transformer.js` | the same |
| `registrar` | `<coreRoot>/harness-registrar.js` | the same |
| `interpretCaseModule` | `<coreRoot>/src/adapters/jest/interpret-case/jest-interpret-case-adapter` | `<coreRoot>/dist/src/adapters/jest/interpret-case/jest-interpret-case-adapter` |
| `resolveEntryModule` | `<coreRoot>/src/adapters/jest/resolve-entry/jest-resolve-entry-adapter` | `<coreRoot>/dist/src/...` likewise |
| `probeRuntimeModule` | `<coreRoot>/src/adapters/jest/probe-runtime/jest-probe-runtime-adapter` | `<coreRoot>/dist/src/...` likewise |
| `probeInjectModule` | `<coreRoot>/src/adapters/jest/probe-inject/jest-probe-inject-adapter` | `<coreRoot>/dist/src/...` likewise |
| `harnessModule` | `<coreRoot>/index` | `<coreRoot>/dist/index` |

Module paths carry no extension. In the source tree the resolver finds the `.ts` file, because no `.js` sits beside
it. In the `dist` tree it finds the `.js` file before the `.d.ts`. That is how `require('./dist/adapters')` works
today.

The runner requires each module file directly, not the `adapters` barrel. Two reasons:

- `adapters.ts` re-exports every adapter, ts-morph's included. The nested Jest has a fresh module registry per test
  file, so the barrel loads ts-morph and TypeScript again for every run. Source mode would also make the nested
  ts-jest compile every adapter on a cold cache.
- The architecture forbids a new root-level barrel, so a narrow `runtime.ts` at the core root is not an option.

The relative module paths, the `dist` folder name, the ceremony file names, the global's name and the source-mode
condition list live in one statics file, `coreRuntimeStatics`. The transformer is the only reader of the paths.
When A-3 moves the jest adapters, it edits that statics file and nothing else on this route.

### How the tree reaches the nested Jest

`jestRunCliAdapter` takes `runtime` in place of `coreRoot`. It builds this config (key order as shown):

```js
{
  rootDir: repoRoot,
  roots: [runsRoot],
  testEnvironment: 'node',
  // source tree only; the key is absent for dist
  testEnvironmentOptions: { customExportConditions: ['source', 'node', 'node-addons'] },
  globals: { __assayerCoreRuntime: runtime },
  setupFiles: [runtime.setupFile],
  testMatch: [`${runsRoot}/**/*.test.js`],
  moduleNameMapper: { '^@assayer/core$': runtime.registrar },
  reporters: [],
  transform: {
    '^.+\\.tsx?$': ['ts-jest', {
      diagnostics: false,
      astTransformers: { before: [{
        path: runtime.astTransformer,
        options: { probeDir, analyzerContentHash, probeInjectModule: runtime.probeInjectModule },
      }] },
    }],
  },
}
```

- **The `globals` entry** carries the whole `runtime` object. Jest copies `globals` onto the test environment's
  global object when it builds the environment, before any setup file runs
  (`node_modules/jest-environment-node/build/index.js:162` — "(0, _jestUtil().installCommonGlobals)(global, projectConfig.globals, globalsCleanupMode);").
  `probe-runtime.js` reads `globalThis.__assayerCoreRuntime.probeRuntimeModule`. `harness-registrar.js` reads
  `globalThis.__assayerCoreRuntime.harnessModule`. Both load inside the nested test environment, so both see it.
- **The transform `options`** carry `probeInjectModule` for `probe-transformer.js`. ts-jest folds `options` into its
  cache key, so source and `dist` output never share a cache entry.
- **The shim** needs no flag. `runUnitBroker` writes the two module paths into it directly.

### Why the config stays identical for every file

Every value above is fixed for the life of one process. `coreRoot` comes from find-up or the harness constant.
`__dirname` never changes. `probeDir` and `analyzerContentHash` are already fixed per process. So two runs in one
process build byte-identical config JSON, and ts-jest keeps one compiler. `jest-run-cli-adapter.test.ts`'s
"two different runs => the config is IDENTICAL" test keeps guarding this, now for both trees.

### Hashing the specimen run artifacts

`npm run test:syntax` writes no run artifacts. Its tests call the analyzer brokers directly, and its tsconfig
`paths` map every `@assayer/core/*` import to core source
(`smoke-repo/packages/syntax-repository/tsconfig.json`, for example
`"@assayer/core": ["../../../packages/core/index.ts"]`). The artifacts come from `assayer unit` run over every
specimen. They land in `tmp/p0-5b-hash/assayer/.assayer/cache/runs/<runId>/`. Each run folder holds `cases.json`,
`run.json`, `console.txt` and the shim `assayer.test.js`. The shim names the runtime module paths, so it differs
between trees by design and is not hashed.

One-time setup, from the repo root:

```bash
A=/home/brutus-home/projects/assayer
H=$A/tmp/p0-5b-hash
C=$H/assayer
mkdir -p $C
printf '{"repoRoot":"%s/smoke-repo","exclude":[],"stableBranch":"master"}\n' "$A" > $C/assayer.config.json
python3 -c "
import os
r='$A/smoke-repo'; out=[]
for d,_,fs in os.walk(os.path.join(r,'packages/syntax-repository/src')):
  for f in fs:
    if f.endswith(('.ts','.tsx')) and not f.endswith(('.test.ts','.test.tsx','.harness.ts')):
      out.append(os.path.relpath(os.path.join(d,f), r))
open('$H/specimens.txt','w').write('\n'.join(sorted(out))+'\n')"
```

On 2026-09-30 that list held 117 files.

One run, with `L` set to `before`, `after-source` or `after-dist`:

```bash
rm -rf $C/.assayer
# before and after-dist: the built CLI
(cd $C && node $A/packages/cli/dist/bin/assayer.js unit $(cat $H/specimens.txt)) > $H/$L.out 2>&1; echo "exit $?" >> $H/$L.out
# after-source instead: the CLI from source, with no build
(cd $C && $A/node_modules/.bin/tsx --conditions=source $A/packages/cli/bin/assayer.ts unit $(cat $H/specimens.txt)) > $H/$L.out 2>&1; echo "exit $?" >> $H/$L.out
python3 -c "
import hashlib,os
runs='$C/.assayer/cache/runs'
for rid in sorted(os.listdir(runs)):
  for name in ('cases.json','run.json','console.txt'):
    p=os.path.join(runs,rid,name)
    if os.path.exists(p): print(hashlib.sha256(open(p,'rb').read()).hexdigest(), rid+'/'+name)
" > $H/$L.sha256
```

The exit code is not 0, because the sad-path specimens fail on purpose. It must match across the three runs.

Compare:

```bash
diff $H/before.sha256 $H/after-source.sha256 && diff $H/before.sha256 $H/after-dist.sha256 && echo IDENTICAL
diff $H/before.out $H/after-source.out; diff $H/before.out $H/after-dist.out
```

Both `diff` pairs must print nothing. If a file differs, run `before` a second time first. A difference between two
`before` runs is a determinism bug outside this item.

## Risks

- **A-3 touches the same route.** A-3 moves the jest adapters out of `adapters/`. With this design, A-3 edits only
  `coreRuntimeStatics.modules` for those paths. The shim generator, the run-cli adapter and the three ceremony files
  hold no module path any more. A-3's planner reads this item's diff first. The EPIC's A-3 row still describes the
  `dist/adapters` string and should be reworded once this lands.
- **A-7 and Phase X move the barrels.** The runner no longer requires `adapters.ts`, so A-7 can remove it freely.
  `harnessModule` names the root `index`. When X-1 moves core's `.` entry, that one statics value moves with it.
- **Core's `dist` layout.** The `dist` paths assume `rootDir: "./"`, which P0-5 keeps (`items/p0-5.md` line 77). If a
  later item changes it, every `dist`-tree run errors. The O-5 hash run catches that.
- **The CLI integration tests read `dist`.** `packages/cli/test/harnesses/assayer-cli.harness.ts:28` — "const cliEntry = join(__dirname, '..', '..', 'dist', 'bin', 'assayer.js');" — and `assayer-compile.harness.ts:47` spawn the built binary. Once the build step is gone, those tests read whatever `dist` exists. EPIC rule 14 says "After P0-5b, integration reads source too". That holds for core's in-process integration test only. See Decision 1.
- **The `test:syntax` claim in D10 and the EPIC row is wrong.** Both say `test:syntax` reads a stale `dist`. Its
  tsconfig `paths` send every core import to source, so it never reads `dist` and never reaches the runner. P0-5b does
  not change it; O-6 is a regression check only.
- **The source condition also applies to the subject's imports.** In the source tree the nested Jest resolves the
  specimens' own imports with `source` added. A third-party package with a `source` export key would switch files.
  None is known; the hash comparison catches it.
- **The nested ts-jest compiles core source with the consumer's tsconfig.** No `tsconfig` option is set, so ts-jest
  finds one by walking up from `rootDir`. For the smoke-repo that is the repo-root `tsconfig.json`. Diagnostics are
  off. A tsconfig that emitted ES modules would break core's `require` calls, but source mode only happens inside
  this repo.
- **A cold ts-jest cache is slower once.** The first source-tree run compiles the runtime modules and shared's
  contracts. Later runs read ts-jest's disk cache. It is still one compiler per process.
- **The global name enters the subject's scope.** `__assayerCoreRuntime` sits on the nested test's global object, as
  `__P` already does. A specimen that enumerates `globalThis` would see it. None does.
- **The home sandbox.** Deleting assayer's `globalSetup` override lets the published sandbox setup run, which the
  published teardown needs. Batch 1's check proves both point at the published files. If the teardown ever ran
  without the setup, it would delete the real `$HOME` (`items/p0-5.md` lines 175-180).
- **P0-5 edits `scripts/jest-global-setup.js` and this item moves it.** Nothing else imports it; O-0 and Batch 1
  confirm that.

### Decisions for the operator

1. **The CLI integration tests.** Option A: keep them spawning the built CLI, and treat them as tests that need a
   current build. The operator builds before running them, and EPIC rule 14 says so. Option B: Batch 8 switches both
   harnesses to `tsx --conditions=source`, as dungeonmaster's own CLI harness does. Option B adds risk: any CLI code
   that reads its own `dist` files, such as the `package.json` that `copy-dist-package-json.mjs` copies for
   `assayer version`, behaves differently from source. Recommended: A now, and B as a follow-up item.
2. **Where the tree is chosen.** This plan puts the choice in `runUnitBroker`, not in `run-paths-broker` and
   `run-each-layer-broker` as the EPIC row says. `run-each-layer-broker.ts` therefore needs no edit. The operator
   should confirm the departure and correct the row.

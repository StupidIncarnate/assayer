# Z-4: which TypeScript Assayer runs, and what core's tarball ships

This item answers two questions from root `CLAUDE.md`'s section "Known defect: core is not ready to publish". It
also settles EPIC row D7.

- **Tarball: fixed.** Core's `package.json` now has a `files` allowlist and a `prepack` build step. The gateway
  `@assayer/npm` now has a `prepack` build step too. Both packages keep the publish state they had: core keeps
  `"private": true`, because nothing in this epic publishes.
- **D7: decided, but code changes still have to follow.** Assayer uses one TypeScript for everything it decides
  itself. That is the copy ts-morph bundles. `typescript` becomes a `peerDependency` of core and of `@assayer/npm`.
  It stays only because ts-jest needs it. The decision needs code changes, so this item does not apply it. Both
  `package.json` files still declare `typescript` as a regular dependency. The follow-up item's file list is at the
  end.

Every number below comes from one run on 2026-10-01, on branch `brands-gateways`.

## 1. D7: measurements

### ts-morph bundles its own TypeScript

- `node_modules/ts-morph/package.json`: version `26.0.0`. Its dependencies are `@ts-morph/common: ~0.27.0` and
  `code-block-writer`. It has no `typescript` dependency and no `typescript` peer dependency.
- `node_modules/@ts-morph/common/dist/typescript.js` is a full TypeScript compiler, 9,066,411 bytes, with
  `version = "5.8.3"`. `ts-morph-common.js` loads it with `require('./typescript')`, never with
  `require('typescript')`.
- The top-level `node_modules/typescript` is also `5.8.3`.
- `node -e "const a=require('ts-morph').ts, b=require('typescript'); console.log(a.version,b.version,a===b)"`
  prints `5.8.3 5.8.3 false`. These are two separate copies of the compiler. They agree today only because both
  version numbers happen to match.

The bundled copy cannot be swapped out. A consumer's `typescript`, at any version, never reaches ts-morph. So
the walk, the coverage IDs, the probe-site offsets and the second, `node_modules`-aware project in
`external-signature/read-declaration` always parse with the version that Assayer's own `ts-morph` pins.

### Code that calls the `typescript` package directly

`discover` for imports of `#gateway/npm/typescript` and `typescript` in assayer's packages found these callers:

| Caller | What it does with TypeScript | Which side |
|---|---|---|
| `packages/core/src/brokers/import-specifier/resolve/import-specifier-resolve-broker.ts`, through the gateway's `resolveModuleFile` | `resolveModuleName`: turns an import specifier into a file for the stitch | analysis |
| `packages/core/src/brokers/tsconfig/read/tsconfig-read-broker.ts`, through the gateway's `readNearestTsconfig` | `findConfigFile`, `readJsonConfigFile`: the compiler options the resolver uses | analysis |
| `packages/core/src/guards/is-assayer-harness/is-assayer-harness-guard.ts` | parses a `*.harness.ts` file to find the `assayerHarness` call | analysis |
| `packages/core/src/brokers/harness/load/harness-load-broker.ts` | `transpileModule` on a harness at compile time | analysis |
| `packages/core/src/transformers/probe-inject/*.ts` | type-only import. At run time `ts` arrives from ts-jest (`compilerInstance.configSet.compilerModule`, in `packages/core/probe-transformer.js`) | emit |
| `packages/@gateway/npm/src/typescript/**` | the gateway wrapper and its proxies and stubs | both |

Nothing else in `packages/` imports `typescript`. Every other parse goes through `#gateway/npm/ts-morph`.

### What ts-jest needs

- `ts-jest@29.4.0` declares the peer dependency `typescript: ">=4.3 <6"`.
- ts-jest picks its compiler with `importer.typescript(..., options.compiler ?? 'typescript')`
  (`node_modules/ts-jest/dist/legacy/config/config-set.js:204`). The `compiler` option can name any module that
  exports a TypeScript API.
- Three ts-jest files also call `require("typescript")` directly, whatever `compiler` says:
  `legacy/ts-jest-transformer.js`, `legacy/compiler/ts-compiler.js` and
  `transpilers/typescript/transpile-module.js`. Two of them read only enum constants (`ModuleKind`,
  `NewLineKind`). `ts-jest-transformer.js:189` transpiles a `.js` file from `node_modules`, and Assayer's transform
  pattern `^.+\.tsx?$` never sends one there. `transpile-module.js` does real work. ts-jest reaches it only when
  the consumer's tsconfig sets `isolatedModules: true` and `module` is `node16`, `node18` or `nodenext`
  (`ts-compiler.js:228-236`).
- So ts-jest always needs some `typescript` package installed, even when its `compiler` option points somewhere
  else.

### Can two TypeScripts disagree about one file?

Yes. With today's regular dependency, a consumer repo can hold three copies:

1. ts-morph's bundled 5.8.3, for the walk and the coverage IDs.
2. Core's own `typescript ^5.8.3`. npm nests it under `@assayer/core/node_modules` when the consumer's root
   version does not satisfy that range. Module resolution, the tsconfig read and harness loading use it.
3. The consumer's root `typescript`. ts-jest is hoisted to the root, and its peer is met from there, so ts-jest
   compiles the code under test with the consumer's version.

Where they can disagree:

- **Probe placement.** The analyzer records each probe site as `start` and `end` offsets, taken from ts-morph's
  parse. `probe-visit-node-layer-transformer.ts:51` matches those offsets against nodes from ts-jest's parse.
  Two compiler versions agree on offsets for syntax both of them parse. For syntax only one of them knows, a site
  can miss its node. The case then reports that it reached no exit, against code that is correct.
- **Resolution.** A tsconfig option known to one version and not the other can change what `resolveModuleName`
  returns. The stitch then disagrees with the ts-morph project that read the external signatures.
- **Determinism.** The resolved index is keyed on the repo layout and a tsconfig hash. The analyzer hash covers
  only core's and shared's own code (`packages/cli/src/brokers/analyzer-roots/resolve/analyzer-roots-resolve-broker.ts`).
  Neither key includes a TypeScript version. If the
  analysis side read the consumer's TypeScript, the consumer could upgrade it and get different resolved edges
  under the same cache key. That breaks root CLAUDE.md's rule "the same code must always produce the same derived
  artifacts".

The coverage IDs themselves are safe in every option. Only ts-morph produces them, and ts-morph's copy is fixed.

## 3. D7: decision

**Option C.** Assayer runs everything it decides on one TypeScript: the copy ts-morph bundles. `typescript`
becomes a `peerDependency` of `@assayer/core` and of `@assayer/npm`, with ts-jest's own range, `>=4.3 <6`.

Why:

- It is the only option where the walk, the resolver, the harness gate and the compiler that places the probes
  are one object. Probe offsets come from the same parser that applies them.
- The TypeScript version becomes a function of Assayer's own lockfile, through `ts-morph`. A consumer's
  environment cannot change any analysis artifact. That keeps the determinism rule.
- There is no second version to keep in step by hand. Bumping `ts-morph` bumps everything together.
- The peer dependency gives the consumer one shared copy for ts-jest and for their own `tsc`. Assayer installs no
  extra copy for itself.
- Option A is simpler, but it leaves two versions on the analysis side and ties artifacts to the consumer's
  install. Option B costs a manual pin that every upgrade can forget, and it still does not control ts-jest.

What the follow-up has to do:

1. `packages/@gateway/npm/src/typescript/typescript.ts` re-exports `ts` from `ts-morph` instead of the
   `typescript` package. `resolve-module-file`, `read-nearest-tsconfig` and their proxies and stubs import the
   same object. Type imports such as `CompilerOptions` come from ts-morph's `ts` namespace too.
2. `is-assayer-harness-guard.ts` and `harness-load-broker.ts` keep importing `#gateway/npm/typescript`. Step 1
   changes what that import holds, so their source does not change.
3. Add a plain-JS ceremony file at core's root that does `module.exports = require('ts-morph').ts`. List it in
   `statics/core-runtime` and in core's `files`. `run-execute-cases-broker.ts` passes its path to ts-jest as
   `compiler`. The config stays identical for every file, so ts-jest still keeps one compiler.
4. Keep ts-jest off `transpile-module.js`, the one path that compiles with the peer copy. Either pass a fixed
   `tsconfig` override in the same ts-jest options, or report it as a P1 error. Measure which one first.
5. Move `typescript` from `dependencies` to `peerDependencies` in both `package.json` files, with range
   `>=4.3 <6`. Keep it in the root and gateway `devDependencies`, where `tsc` builds the repo. Check that
   `dungeonmaster gateway-sync`, which the root `postinstall` runs, does not regenerate a `typescript` folder from
   a dependency list that no longer names it.
6. Delete the typescript bullet from root CLAUDE.md's "Known defect" section.

Follow-up file list: `packages/@gateway/npm/src/typescript/**`, `packages/@gateway/npm/package.json`,
`packages/core/package.json`, a new ceremony file at `packages/core/`,
`packages/core/src/statics/core-runtime/core-runtime-statics.ts` and its test,
`packages/core/src/transformers/core-runtime/core-runtime-transformer.ts` and its test,

Two related problems stay open:

- `ts-jest@29.4.0`'s peer range ends below TypeScript 6. A consumer on TypeScript 6 gets a peer conflict from npm,
  whichever option is chosen, because ts-jest is a core dependency.
- The analyzer hash does not cover the `ts-morph` version. A ts-morph bump changes the parser without changing the
  hash, so old cache entries survive it.

## 4. The tarball: measurements

All runs used `--ignore-scripts`, so the new `prepack` did not build anything.

### Core, before the change

`npm pack --dry-run --json --workspace=@assayer/core` gave 785 entries, 689,216 bytes packed and 3,217,956 bytes
unpacked. Root `.gitignore` lists `dist`, and core had no `files` list, so npm used the gitignore and left `dist`
out. The tarball shipped:

- no `dist/` at all, so every `import`, `require` and `types` target in `exports` was missing;
- 291 `.test.ts` files, 117 `.proxy.ts` files and 61 `.stub.ts` files under `src/`;
- `CLAUDE.md`, `index.ts`, `jest.config.js`, `tsconfig.json`, `tsconfig.build.json` and 10 files under `test/`;
- the three ceremony files at the root: `probe-runtime.js`, `probe-transformer.js` and `harness-registrar.js`.

### Core, after the change

`npm pack --dry-run --json --ignore-scripts --workspace=@assayer/core` gives 1,204 entries, 500,680 bytes packed
and 2,136,097 bytes unpacked:

- `package.json`;
- `dist/`: 1,200 files, the `.js`, `.d.ts` and their maps. `dist/package.json`, a build-time copy for the CLI's
  `--version`, is excluded;
- `probe-runtime.js`, `probe-transformer.js` and `harness-registrar.js`.

No test, proxy, stub or source `.ts` file ships. Every `exports` target a consumer without the `source` condition
can reach is in the list:

| Key | Condition | Target | In the tarball |
|---|---|---|---|
| `.` | `import`, `require` | `dist/index.js` | yes |
| `.` | `types` | `dist/index.d.ts` | yes |
| `./brokers` | `import`, `require`, `types` | `dist/src/brokers/brokers.{js,d.ts}` | yes |
| `./contracts` | `import`, `require`, `types` | `dist/src/contracts/contracts.{js,d.ts}` | yes |
| `./transformers` | `import`, `require`, `types` | `dist/src/transformers/transformers.{js,d.ts}` | yes |

The run-time modules `coreRuntimeTransformer` loads by path also ship:
`dist/src/brokers/case/interpret/case-interpret-broker.js`,
`dist/src/brokers/case/resolve-entry/case-resolve-entry-broker.js`,
`dist/src/brokers/probe-runtime/create/probe-runtime-create-broker.js`,
`dist/src/transformers/probe-inject/probe-inject-transformer.js` and `dist/index.js`.
`run-paths-broker` finds core's root by walking up to `probe-runtime.js`, so that file has to ship at the
root.

### Proxies and stubs do not belong in the published package

`discover` for `@assayer/core/...proxy` and `...stub` imports finds them only in the proxies and tests of
`packages/cli` and `packages/desktop`. Those are workspace siblings, and their Jest runs set the `source`
condition. A consumer's harness imports only `assayerHarness` from `@assayer/core`. Core's `tsconfig.build.json`
already excludes `**/*.proxy.ts` and `**/*.stub.ts`, so `dist` has no compiled copy to point at.

So `./*.proxy` and `./*.stub` keep only the `source` condition, which EPIC row X-1 also requires. A consumer
without that condition gets Node's `ERR_PACKAGE_PATH_NOT_EXPORTED`. That is the right answer for a test seam that
is not part of the public API. The comment in `run-execute-cases-broker.ts:65-66` already states the same
assumption: "a published core ships no TypeScript for a `source` condition to resolve to".

### `prepack`

Core's `prepack` is `node ../../scripts/build-workspaces.mjs --tsc-only`. A plain `npm run build` inside core is
not enough on a fresh checkout. Core's build reads the types of `@assayer/shared` and the gateways from their
`dist`, and nothing would have built those yet. The root script builds every package with a
`tsconfig.build.json`, in dependency order. It runs from `REPO_ROOT`, so the package directory npm starts it in
does not matter.

### `@assayer/npm`

Measured with the same command. Before and after: 145 entries, `dist/` plus `package.json`. Its `files: ["dist"]`
was already correct. Every target was checked against the list: each `src/<name>/` folder has
`dist/<name>/<name>.{js,d.ts}` (`./*`), and each `.proxy.ts` and `.stub.ts` in `src` has its `.js` and `.d.ts`
in `dist`.

It had the same missing step as core, though. It has no `prepack`, and `dist` is gitignored, so a pack from a
fresh checkout would ship only `package.json`. It now has
`"prepack": "node ../../../scripts/build-workspaces.mjs --tsc-only"`. It is not marked `private`, and this item
does not change that.

## 5. Still blocking a publish of core

- Core keeps `"private": true`.
- Core depends on `@assayer/shared`, which is also `"private": true`. Core cannot be installed from the registry
  until shared can be.
- The D7 follow-up above.
- `analyzer-roots-resolve-broker.ts` returns `[]` outside the monorepo. Its own doc says the fingerprint then
  "degrades to a constant: it over-caches, never mis-caches". In a published install the analyzer hash would
  therefore never change, and a cache written by one Assayer version would be reused by the next.
- The gateways `@assayer/bin`, `@assayer/node` and `@assayer/browser` have `files: ["dist"]` and no `prepack`,
  the same gap `@assayer/npm` had. They were outside this item's file list.
